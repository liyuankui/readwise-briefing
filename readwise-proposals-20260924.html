Proposal 2 · Muse-Lite Life OS × OpenMuse

连接：Life OS Next ②≤500 行 Bun SQLite🔬 亲测输入

借 OpenMuse Activity 层，把 agent 群从「能跑」升级到「靠得住」

核心主张：不 fork OpenMuse，只抽其 Activity 层设计（durable task plan + SQL lease + approval + receipt），以 ≤500 行 Bun+TypeScript SQLite ledger 替换现有 status.json/catchup 机制，并用它承载拖延 5 个月的「第一个 Proactive Agent」——一次落地，同时关闭 Life OS Next ② 并打下 Trust & Eval 地基。
关键侦察发现（subagent 实读 workspace/life-os/）
  • Life OS 已有 12 agents + 425 行 run-agent.sh + catchup v0.4 + registry.json——已是自研半套 Activity 层，本提案只补语义层不另起炉灶
  • catchup.sh 每 2h+开机双触发可双跑（无 lease 防重）——痛点自证
  • Browser worker 明确出局：现有 12 agents 无一需要 Chromium

Proposal 3 · mem-index 统一检索层 Life OS Memory × LightMem-Ego

连接：Life OS Next ③≤6h/周 硬封顶✅ 论文+代码验证

借 LightMem 分层思想，不引其系统——先让 4907 个文件变得可查

核心主张：不为 Kyle 引入 LightMem-Ego 式新记忆系统，而是借其「三级记忆 + 自动巩固」思想，在现有 IRA 之上补一个可随时重建的派生层——统一检索（Bun + SQLite FTS5 全库索引，单一 mem.query 入口）+ 巩固管线（一次性事实 → 长期规则的 AI 提案制晋升）。IRA 与 git 仍是唯一 source of truth。
关键侦察发现
  • 实测 4907 个 md / 296MB：journal 737 篇、context 2740、workspace 924；唯一人工索引 context/INDEX.md 仅 246 行
  • 五类 store 零互通（git md / state.json / Keychain / store_memory / 对话摘要），检索靠 grep + 人指路
  • IRA 与 Atkinson-Shiffrin 三级模型天然同构：inbox=感觉记忆、workspace=短期、context+journal=长期——缺的不是分层结构，是层间巩固机制
里程碑（每周 ≤6h，吸取 CS336 停滞教训）
M内容估算
M0记忆普查 + 10 问盲测基线（hit 率写死，预期 <50%）W1, 3h
M1mem-index MVP：全库 FTS5 索引 + mem.query；重建 <5minW2-3, 16h
M2巩固管线 v0：一次性事实 → AGENTS.md 提案制晋升（人不批不写）W4-5, 10h
M3单一生活流试点（仅日程 .ics → 月度摘要）W6-7, 8h
M420 问盲测复测 + 决策门（是否上向量/第二生活流）W8, 3h
成功标准
  • 盲测 hit@1：<50% → ≥80%；查询 P95 <2s；人工指路次数周降 70%
  • 巩固提案 ≥2 条/周，人审通过率 ≥50%；索引仅本地不入 git（隐私）
诚实挑战（节选）：① 三轴全异（GB 级音视频流 vs KB 级文本、端侧实时 vs 离线、眼镜算力 vs Mac）——LightMem-Ego 工程实现对 Kyle 场景几乎零适用，可复用代码 <10%；值钱的是 STM→LTM 的 salience 提炼与遗忘策略设计。② GBrain 大爆炸提案搁置 4 个月反证：被推迟的检索层才是正确第一步。③ 学术 demo 直接跑 repo 要两周，读论文借设计只要 2 小时——选后者。

Proposal 4 · 测试策略 Oracle 分层 AI Coding Eval × 「E2E 优先」观点

连接：AI Coding Eval · Qoder Pilot · 双 skill12 人日 / 3-4 周⚠️ 争议信号输入

重配 Agent 时代的测试金字塔，并解 Eval 满分饱和

核心主张：Agent 时代的测试策略不做 unit vs E2E 站队，而做 oracle 分层配比：E2E 金路径锚定业务终态（每域 5-8 条、夜间）、hidden unit suite 密集守业务规则、contract 守服务边界；agent 自产测试须过反自我确证审计（mutation kill ≥70% + mock 配额 ≤30%）方可入库。
信号裁决：取机制，弃处方
  • ✅ 取：oracle 独立性（agent 代码后自写测试 = 同源误解自我背书）、E2E 可复验 artifact、测试先行的时序直觉
  • ❌ 弃：「NEVER unit」二分站队、「E2E as sole mechanism」（经济学不成立）、盲抄进团队 AGENTS.md（+19% 推理成本无对等收益）
主战场：Eval 满分饱和
  • 三异构模型 FTP 满分 = 区分度 0 = 该维度对选型信息量趋零；更难堪的对称：若 FTP 测试对 agent 可见，满分可能只是「对着测试编程」的胜利
  • M1 饱和诊断（本周 2 人日）：抽 10 个满分 case 测 mock 比例 + mutation kill → 裁决「判定面窄 / 任务太易 / 模型真同强」
  • ⚠️ 保守纪律：M1 裁决前，满分不得作为选型背书写入 Qoder Biz Case
ROI
  • Qoder Biz Case 恰缺「质量不显著下降」的量具——M1 国庆收口前补上质量护栏段
  • 选型资金护栏：饱和 benchmark 导致错误选型的切换成本 ≈ 2-4 人周；打回率降 30% 可进 FY27 benefit ledger
  • llm-as-qa-judge 现成 Checkout/Inventory domain checks（超卖/幂等/并发扣减）即 hidden suite 素材——两资产直接咬合
立即行动（本周）
  1. 抽 10 个 FTP 满分产出 → mock 比例 + PIT kill-rate 一页诊断（0.5 天，Kyle+1 工程师）
  2. A/B 微实验：同一库存扣减任务「测试可见 vs hidden oracle」× 三模型（2h，直接验证自我确证机制是否存在）
  3. unit-test-best-practices 挂 v2.0 三规则草稿（oracle 独立性/mock 配额/mutation 自检，先 append）
诚实挑战（节选）：① E2E-only 在 11 人 Java/K8s 电商团队不现实可量化：全链路分钟级反馈摧毁 agent 自纠错循环、flaky 率随依赖数上升、跨 N 服务定位 O(链长)——E2E 的正确位置是塔尖。② 订单/库存的纯逻辑组合爆炸（超卖/幂等/状态机）只有 unit+property-based 经济可覆盖——推文骂的是「谁来判定」，不是「测哪一层」。③ skill 实读发现：unit-test-best-practices v1.1.0「NOT to use: 端到端集成」已不合 agent 时代，judge 四维全测「写了什么」无一维测「能否抓住错」——两 skill 均需演进。
