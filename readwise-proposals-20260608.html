Life OS Software Factory：从 Prompts 到 Loops

人负责写状态机，LLM 只在不确定节点做判断
→ 连接项目：Life OS Software Factory 🌱
"我写 loops" 的具体含义是：人负责写状态机（state, budget, stop condition, eval），LLM 只在不确定节点做判断；Software Factory 由代码驱动，不由一次性 prompt 驱动。

🔓 Loop 解锁的能力

痛点Prompt 模式做不到Loop 模式解锁
跨时间执行一次对话结束即失忆持续 watch CI / retry / resume
可验证交付常停在"已生成代码"必须过 test / PR / eval 才结束
主动运行需要 Kyle 召唤schedule/event 自动触发
失败恢复失败即人工接管有状态重试、降级、告警

💻 PR Autopilot Loop 伪代码

while (factory.isOpen()) {
  const task = queue.pickApproved("autopilot-safe");
  if (!task) break;

  const ctx  = loadContext(task);
  if (!riskGate(task, ctx)) { notifyHuman(task, "risk"); continue; }

  const branch = git.createBranch(task.id);
  let passed = false;

  for (let i = 0; i < 3; i++) {          // 最多 3 轮
    const plan   = llm.plan(task, ctx, lastFailure);
    apply(plan.diff);
    const test   = runTests(plan.testScope);
    const verify = evaluate(diff(), test, policy);

    if (verify.pass) { passed = true; break; }
    lastFailure = summarizeFailure(test, verify);
    rollbackUnsafeChanges();
  }

  if (!passed) { escalate(task, lastFailure); continue; }

  const pr = gh.openPR(task, diffSummary());
  const ci = watchCI(pr, { timeoutMin: 30 });

  if (ci.fixable) reenterLoop(task, ci.logs);
  else            notifyHuman(task, ci.status);

  recordMetrics(task, pr, ci);
}

📏 成功标准

1个 autopilot-safe 任务 无需手动触发即生成 PR
PR 前 test 通过；CI 结果被系统追踪到终态
连续2周 无重复取单/脏分支/无限重试
≥60% 自动 PR 可直接 merge 或仅需轻微 review

⚡ 立即行动

  • 定义安全任务类型：列出 10 个 autopilot-safe 样例任务（依赖升级、lint fix、测试补充）
  • 先实现单仓 patch-test loop：不开 PR，只做到本地 test pass
  • 接上 PR + CI watcher：在 Life OS 自仓跑通 1 次完整链路
⚠️ 诚实挑战：Loops 不是万能隐喻。它擅长 bounded work：状态清晰、验证明确、失败可分类。若问题本质是"该不该做"而非"怎么反复做到对"，loop 会把不清楚的战略问题包装成高效忙碌。先别让 Agent 写任何代码，先让它稳定完成一种小而闭环的代码循环。

CDH Agentic Engineering Playbook：生产三模式落地

不投资"多 Agent 并行写代码"，构建受控型编排体系
→ 连接项目：Engineering Baseline + AI Adoption Strategy 🔥
CDH 应构建"Single-Writer + Shared Context + Controlled Delegation"的 Agentic Engineering 体系，而不应投资"多 Agent 并行写代码"的自动化幻觉。

⚔️ 三种模式 vs 常见失败做法

生产可活模式常见失败做法为何会死
Single-Writer / Multi-Advisor多 Agent 同时改代码冲突、覆盖、责任不清
Context Engineering（共享状态）只优化 prompt上下文碎裂，结果漂移
Task Decomposition + Delegation放任 agent swarm 探索成本失控，难验收

🗓 实施里程碑（12 周）

  • W1-2M1. 选 3 个场景（Incident RCA、PR Review Assist、Tech Debt Refactor）；建统一任务模板；定义 Single-Writer 规则；建 baseline 指标
  • W3-5M2. 为每个场景建 Shared Context Pack（system map, runbook, ownership, constraints）；输出《CDH Context Playbook》
  • W6-8M3. 落地 Writer/Advisor/Reviewer/Verifier 四角编排；禁止多 Agent 并发写同一 worktree
  • W9-12M4. 度量 ROI；沉淀《CDH Agentic Engineering Playbook v1》；决策是否扩面

📏 成功标准

PR lead time 降低 15-25%
Incident MTTR 降低 20-30%
AI 生成代码被回滚 <5%
≥70% 工程师每周 3次+ AI 工程任务

⚡ 立即行动

  • 产出统一 Task Contract：Goal / Context / Constraints / Done / Evidence
  • 开 60 分钟训练营：主题"怎么让 AI 听懂我：Prompt 不如 Context"
⚠️ 诚实挑战：CDH 适合受控型 multi-agent，尚未准备好 autonomous swarm。缺的前置条件：统一 Context Engineering discipline、标准化任务拆解方法、可追踪 ROI metrics、清晰 agent 权限模型。若今天直接推"多 Agent 自动写代码"，大概率制造更多 output，而非更多 outcome。

Dynamic Harness Generation：让测试变便宜的机器

先造底座，再批量产测；AI 不只写 @Test，先建 CheckoutHarness
→ 连接项目：Testing Excellence + AI Upskill Trainer 🔥
把测试策略从"人工补 testcase"升级为"AI 先按模块生成专用验证底座，再批量产测并迭代"——测试不再是手工艺，而是可复制能力。

💻 动态 Harness 示例（checkoutService）

class CheckoutHarness {
    final FakeInventoryClient inventory = new FakeInventoryClient();
    final FakePaymentGateway  payment   = new FakePaymentGateway();
    final InMemoryOrderRepo   repo      = new InMemoryOrderRepo();
    final CheckoutService     service   = new CheckoutService(repo, inventory, payment);

    CheckoutRequestBuilder request() {
        return new CheckoutRequestBuilder()
            .withCurrency("CNY")
            .withItem("SKU-1", 1, new BigDecimal("199.00"));
    }

    void givenStock(String sku, int qty)   { inventory.put(sku, qty); }
    void givenPaymentTimeout()             { payment.timeoutNextCall(); }
    void givenIdempotencyKeySeen(String k) { repo.saveIdempotency(k); }

    void assertAmount(OrderResult r, String expected) {
        assertThat(r.getPayableAmount()).isEqualByComparingTo(expected);
    }
    void assertSingleOrderCreated(String key) {
        assertThat(repo.countByIdempotencyKey(key)).isEqualTo(1);
    }
}

🗓 里程碑（试点：checkoutService，6 周）

  • W1基线盘点：核心结算路径、现有测试/CI/JaCoCo 真实基线
  • W2设计 Harness v1：fixture builders、fake adapters、BigDecimal assertions、idempotency helper
  • W3-4AI 批量产测：覆盖 checkout / discount / payment fallback / idempotency
  • W5接入 CI gate：PR 必跑测试；先设 core-path gate，不追全局 60%
  • W6复盘推广：模板化为 Java/Golang 双栈 playbook

📏 成功标准

Core-path coverage ≥40%（6周目标）
新增/修改 PR 带测试率 ≥80%
单个测试用例 lead time 下降 50%
结算类 escaped defect 下降 20%+

⚡ 立即行动

  • 选定 checkoutService owner + tech lead，确认试点边界只含 1 条核心结算路径
  • 做基线审计：真实 coverage、测试数、PR 流程、近3个月结算类 defect
  • 定义 Harness v1 contract：金额精度/库存不足/幂等重试/支付超时 4 类场景
⚠️ 诚实挑战：AI-generated harness 不天然优于人写测试。更优之处：重复、结构化、场景可枚举的 service logic。更差之处：领域规则暧昧、跨服务契约不清、历史债极重时，AI 会把误解自动化。最佳定位：先把 70% 测试底座自动化，人力留给 30% 高价值判断。

从"教个人用 AI"到"让团队以 AI 方式工作"

维度个人 AI 能力建设组织 AI 能力建设
