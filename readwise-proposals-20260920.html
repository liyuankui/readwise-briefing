Proposal A｜Context Compaction 策略升格为 AI Coding Eval 第一等评测维度

状态：提案待审 | 提出：2026-09-20 | 关联：AI Coding Eval、Qoder 试点 | 信号源：JEV（typesafe.ai，2026-09-16 发布）及两个开源 compaction 插件（已 clone 审计源码）

1. 核心主张

长任务场景下，compaction 策略（原生 LLM summary / verbatim pruning / 无压缩+长上下文）对任务成功率与总成本的影响量级可能与模型选型本身相当，而现行所有评测都隐含「compaction 免费」的错误假设——故应将其升格为与 model 并列的第一等 harness 维度，并先用一个可证伪实验验证这次升级是否成立。

经得起追问的原因：这不是断言「JEV 好」，而是断言「一个从未被测过的变量可能是一等变量」——实验结果无论正负都有决策价值（见 §4 预注册两档判定）。

2. 锁定的具体痛点

痛点 具体表现 现有评测为何测不到
10 秒小作文卡顿 Claude Code 上下文一满即触发 LLM 重写式 summary，用户可感知约 10s 停顿；破坏心流，且是试点采纳率的隐藏变量 评测只记总时长，不记「compaction 事件停顿」
summary 有损丢信息 重写式压缩丢的不是随机 token，而是早期 tool_result 中的错误根因、接口契约、早前约束；长任务后期模型"忘了看过什么" → 返工 任务长度从未越过 compaction 阈值
harness 维度区分度耗尽 FTP 场景部分模型已满分——恰是任务太短的证据 区分度只剩 harness，而 harness 目前只测了外围配置

一句话锚定：评测任务不触发 compaction，等于所有「model A 优于 B」的结论都在无效区间的外推。

3. 实施里程碑（总计约 4-6 周，1-2 名工程师兼职）

里程碑 内容 估算
M0 长任务集 构建必触发 compaction 的任务集（会话 ≥150k token，每任务触发 ≥2 次）；先跑 3 任务校验触发率 1 周
M1 三臂对照 同一 model × 三 harness：原生 summary / JEV verbatim pruning（fast-jev 或 omp 实现）/ 无压缩长上下文 2-3 天
M2 指标管道 成功率、token 总成本（含 compaction 自身+后续 cache 命中）、墙钟（含停顿次数×时长）、信息保真度（见 §4） 1 周
M3 运行+统计 多 seed 重复，配对设计，显著性检验 1-2 周
M4 决策报告 产出 model × compaction 矩阵，更新选型建议 2-3 天

4. 成功标准（预注册，防事后合理化）

指标 升格成立（常设维度） 降级（记负结果收档）
长任务成功率差（最好 vs 最差臂） ≥10pp 且配对检验显著 <5pp
信息保真度（埋点事实召回） verbatim ≥90% 且显著高于 summary 两臂无差
单次 compaction 成本 差值 ≥10x（JEV 全量扫描 200k 输入约 $0.008-0.04/次，输出免费；summary 双向计费） 差值 <3x
Compaction 停顿 ≤2s vs 基线 ~10s 无可感差异

关键设计：信息保真度用客观 ground-truth（任务早期埋 N 个关键事实 + 后期检查点行为验证），不依赖 judge——直接绕开当前 57-59% 一致率的评分噪声问题。

5. ROI / 业务影响

  • 选型决策质量：AI Coding Eval 结论直接驱动 Qoder/Copilot 量级的支出；忽略 compaction 的选型可能在长任务上系统性误判。
  • 成本双通道：单次事件成本（输入计费+输出免费 vs summary 输出高价侧）+ prompt-cache 保持（omp 实测 16,198 条消息回放，40 请求仅 3 次 rewrite、0 次 prefix break；重写式 summary 每次必然打碎 cache 前缀）。
  • 返工减少：若成功率差 10pp，按团队规模 × 长任务频率 × 返工时长折算——具体数以 §7 行动 3 的实测频率为准，先测量再承诺。
  • 体验：按每人每天 3 次触发估算（约 750 次/人/年），每次 10s→<2s 的停顿削减是可感知的。
  • 方法论外溢：公开输出可建立团队在 agentic engineering 评测上的话语权。

6. 风险与缓解

风险 缓解
JEV 初创供应链（发布仅数日、2 天 6 个 clone、可能改价/停服） 评测对象是「compaction 策略」抽象维度而非 JEV：插件 MIT 可 fork，verbatim pruning 逻辑约 1k 行可自研替换；成本结论标注有效期
Benchmark 争议（Theo 批评；官方 ~100ms vs 实测 ~400ms） 所有性能数字一律亲测，官方声明仅作参考
与模型长上下文能力混淆 三臂设计正是为分离交互效应；结论表述为 model × compaction，非单主效应
任务不够长，白跑 M0 触发率校验为 gate，不达标不进 M1
评分噪声 本维度全走 ground-truth，不加 judge 负担

7. 立即行动（本周内）

  1. n=1 体验样本（1 天）：个人日常 Claude Code 长会话装 fast-jev-compaction（MIT），记录卡顿感与"忘事"是否回归。
  2. 测量学烟测（2-3 天）：挑现有 eval 最长任务埋 10 个关键事实，compaction 前后各跑一次——验证保真度指标是否可测。这是整个 Proposal 的可行性闸门。
  3. 痛点定量化（半天）：统计近两周团队会话的 compaction 触发频率与停顿时长，把「10 秒卡顿」从轶事变成数字。

8. 诚实挑战

  • 可测性是最软的软肋：功效分析量级——配对连续分数、Δ=10pp、σ=20pp 时约 32 任务/臂；若只能二元判分则需数百任务。团队跑得动前者，跑不动后者。若预算只够前者，本维度现阶段只能出方向性结论，须在报告里明说。
  • 触发长度决定 ROI 成色：任务要多长才触发？若实测团队 90% 会话远低于阈值，compaction 就是低频事件，ROI 叙事退化为"少数超长任务+成本"窄场景——所以行动 3 排在本周而非实验后。
  • 同义反复陷阱：「不重写比重写保留更多信息」近乎定义。非平凡的问题是：保留的信息是否被模型使用、prune 掉的是否真的无害。实验必须能区分「保真度差但成功率平」的情形，否则测的是中间指标不是终点指标。
  • 模型可能通过重读找回信息：tool re-read 会让保真度低但成功率不受损——此时成本/时间仍可测，但"保真度→成功率"因果链须谨慎表述。
  • 长上下文路线的半衰期：no-compaction 臂若平价取胜，本维度价值取决于「窗口增长赶不上任务复杂度增长」这个真赌注；窗口若快速白菜化，整条产品线（含 JEV）贬值。
  • JEV 可能就是 hype：病毒传播+benchmark 争议是典型早期泡沫画像。Proposal 押注策略维度而非供应商，这点已对冲；但若 verbatim pruning 在我们的任务上不胜出，结局是一份价值有限的负结果。

Decision Ask：批准 M0 + 行动 1-3（约 1 人周），一周后凭触发率与保真度烟测数据决定是否进入 M1-M3。

Proposal B｜typed decision model 作为 L0/L1 前置验收层的分层路由器

项目代号 ECHO（AI Coding Eval）× LVP（验证分层协议）｜2026-09-20｜Draft

0. 与 09-18 Judge 提案的关系

09-18 提案回答「L2 层内评分准不准」：先测人人一致率做 rubric 归因诊断，再以 typed criteria（维度×档位）+ 双 backend PoC + 非劣性门槛替换 judge 评分器。本提案不重复该工作，承接其两条产出——rubric 诊断结论（哪些分歧源自评分标准而非模型）与 provider 抽象（OpenJev 等社区复现可直接复用）——解决其未触及的上一层问题：层间路由。即便 09-18 完全成功，judge 仍需处理全量 case；本提案把流量在进入 L2 之前就分流掉，judge 从全量执行器降级为抽样复核器。两提案接口：共用同一批人工已审 case 与检查项清单，不重复建设。

1. 核心主张

LVP 缺的不是更强的 judge，而是 L0/L1 的执行器：验收流水线中天然可枚举为选择题的检查项（其占比可测量，谓之「分层覆盖率」），下沉给 typed decision model 执行——毫秒级延迟、输入侧计费（比 judge 便宜 1-2 个数量级）、输出空间结构性限定为预设选项（无文本可幻觉）——LLM judge 只对残余与抽样样本负责，人工只留 L3 与分歧仲裁。

预期追问 回答
凭什么无幻觉 输出=类型化选项+置信度（由返回分布形状导出），不生成文本；错误形态从「编造」降级为「选错」，可审计
与 09-18 何异 它换 L2 的评分器，本提案决定「哪些检查项根本不必进 L2」；正交且互补
初创供应商凭什么赌 不赌执行器赌资产：检查项清单+类型化问题库 vendor-neutral，JEV/OpenJev/自托管皆可换
judge 降级后谁兜底 双 Kill 线保留；低置信强制升级；judge 抽样分歧直接触发 L3 人工

2. 锁定的具体痛点

痛点 事实锚点
judge 贵 全量读上下文+生成评语；50K-token case 约 $0.18，typed 层 $0.0021-0.01（node 实算，18-86 倍差）
judge 会幻觉且不准 与人工一致率仅约六成（57-59%）；评语可编造，错不可枚举
LVP 空转 验证强度与爆炸半径成正比 + 双 Kill 线已定义，但 L0/L1 无「不幻觉、便宜、快」执行器，长任务验收仍全量压给人/judge

关键未知数（本提案第一交付物）：分层覆盖率——一条验收流水线里多少检查项天然是选择题。 不拍数字，给测量方法（检查项形态标注法）：

  1. 从近 30 天人工已审 case 抽 20 个；
  2. 把每 case 的人工结论分解为原子检查项（1 个 verdict → 3-8 项），得检查项全集 C；
  3. 每项标三类：M（grep/测试/lint 可判，原属 L0）、T（需读上下文但答案可枚举——是否/档位/k 选 1，可下沉 L1）、O（须生成式判断，留 L2/L3）；
  4. 双人独立标注，算 Cohen's κ，分歧仲裁；
  5. 报告 L1 覆盖率 = Σ耗时(T)/Σ耗时(C)（问题数与人工耗时两个口径）。

止损线：耗时加权 T 类占比 <40% → 记录负结果，不立项。

# 里程碑 产出 估时
M1 检查项普查+20 case 改写 分层覆盖率基线；20 case 的 T 类检查项改写为类型化问题（binary/k-way+置信阈值）；回译测试通过（从类型化问题能盲评还原原验收意图，防 Goodhart） 2-3 天

M3 模板库+LVP 集成 类型化问题模板库 v0（≥15 项：是否改测试/是否触碰鉴权/错误是否现于日志/diff 是否越界声明…）；fallback 链 typed→judge→人工；judge 改抽样复核（如 10%） 3-5 天
M4 灰度+度量+vendor 决策 L0/L1 灰度 2 周：分流率/抽样复核一致率/成本/延迟报表；JEV API vs 自托管 break-even 决策 1-2 周含观察

总计约 4-5 周部分投入。

指标 基线 目标 Kill 线

5. ROI / 业务影响

  • 直接成本：typed 层输入侧 $0.042-0.20/MTok、输出免费；50K-token case 演算 $0.0021-0.01 vs judge ~$0.18（假设公开牌价，M2 后以实测替换）；
  • judge 调用降 ≥70% = token 支出同比例下降；
  • 人工带宽：长任务验收是大头；分流 ≥50% 即释放一半 review 带宽回归工程；
  • 资产化：验收结论从「一段生成评语」变为「选项+置信度+阈值」——可聚合、可回归、可做趋势 dashboard；检查项清单与问题库版本化复用（复用率是 ROI 核心变量，M4 必测）；
  • 姊妹信号：Bonsai 2 27B（9x 压缩保留 98.2% 性能）表明小模型自托管成本持续下降，强化 vendor 兜底路径。

6. 风险与缓解

风险 缓解
供应商：JEV 初创单点，已有 6+ clones 质量参差，定价/SLA 未稳 问题库 vendor-neutral；provider 接口承接 09-18 抽象；break-even 前置 M4
表达力边界：设计质量/root cause/「good enough」天然非选择题 这正是分层存在的理由：O 类留 L2/L3；「本 case 是否含 O 类项」本身即可设计为第一个类型化问题
阈值误调致误放行 双 Kill 线不动；低置信强制升级；阈值经标注数据标定并纳入回归（jevcal 模式）
数据外送（code diff→第三方 API） 安全审计先行；高敏场景走自托管 clone
覆盖率虚高（O 类硬塞成 T 类凑数） 回译测试+judge 抽样兜底；标注 κ 公开

延迟争议（标称 100ms，社区实测 70-500ms） 自测 p95；分片并发（fast-jev-compaction 已验证该模式，失败即 throw 由上层 fallback，工程诚实）

7. 立即行动（本周）

  1. （2h）跑形态标注：抽 20 个人工已审 case，分解检查项、标 M/T/O → 分层覆盖率基线；<40% 当场止损；
  2. （0.5 天）写 10 个类型化问题模板：JEV API 跑这 20 case 的 T 类项，对齐人工结论 → 首批一致率/成本/延迟数据点；
  3. （0.5 天）三列对照表：同批检查项「judge 原样 / typed 执行」成本-延迟-一致率对照 → 用实测硬数据替换本提案全部演算。

8. 诚实挑战

  • 我们在用锤子找钉子吗（核心质疑）：最可能的失败模式是 T 类大半本属 M 类（grep/测试已可判），typed 执行器的真实增量只剩「需读上下文的机械问题」——这个交集多大正是 M1 要测的第一未知数；若小，应记负结果而非强行立项。
  • 成本转移幻觉：judge 的推理成本换成了人的问题设计成本，只有模板复用率够高才划算；复用率未验证前 ROI 全是纸面数字。
  • 无幻觉 ≠ 不会错：结构性保证仅限「不编造选项外内容」；系统性选错且带置信度背书，比幻觉更隐蔽——需错误归因台账。
  • 监督者悖论：judge 抽样复核自身与人工一致率仅约六成——用一个六成一致的工具监督一个九成一致的层，效力存疑。缓解：judge 仅作烟雾报警器（分歧即升 L3，容许误报，只怕漏报），不作 ground truth。
  • 路由器的路由器：判断「某检查项是否可枚举」本身仍是人工判断；首轮靠人，规模化后此环节会成为新瓶颈或新的 Goodhart 点。
  • 频谱错配：JEV 成功用例是 compaction（海量高频小决策），验收是低频高价值决策；若模板库小、日均调用个位数，自托管运维成本可能吞掉全部节省——break-even 分析是 M4 的否决项而非形式项。

Proposal C｜Ternary Bonsai 2 27B：「本地零边际成本编程模型」入选评测

1. 核心主张（一句话）

三值量化已把 27B 压进「工程师笔记本区间」（5.9GB 权重、8.6GB 内存、M5 Max 46.8 tok/s），本地边际成本归零；唯一未知数是编程折损——本提案用约 5 人日 FTP 实测把「9x 小、编程掉多少」变成数字，使 opencode 提案从「云端便宜」升级为「云端便宜 + 本地免费且代码不出本机」双档论证。

经得起追问的锚点：主张不是「Bonsai 可用」，而是「该问题当前无人能答（98.2% 为聚合值，coding 子集未公布），且我方一周内具备回答的全部条件——M5 Max 128GB、现成 FTP 评测集、全精度基线可同机运行」。

8. 诚实挑战

  • 46.8 tok/s 对 agent 式多轮编辑，大概率不够。 单次 edit 输出 300-800 token → 6.4-17.1s/次；10 轮任务纯生成约 107s，且单流无并发（云端 80-150 tok/s + 无缝并发）。判定：单人交互式单文件编辑勉强够；批量评测慢 3-5x；「团队共享本地服务器」不成立。若 MLX 4x 提速属实（≈187 tok/s）结论翻转——这正是 M1 将其列为第一测项的原因。
  • 编程对量化的敏感度可能远超聚合 benchmark。 代码 token 长尾（缩进、括号、低频 API 名）恰是三值权重表示力最弱处；98.2% 聚合完全可能掩盖 coding 子集 <90%。禁止外推，必须实测——这意味着结果可能是否定的，而否定同样有信息价值。
  • 区分度反噬。 FTP 已有满分模型，若 Bonsai 轻松满分，评测无增量。须预埋第二维度（延迟/成本/失败模式），否则「过了」只是重复已知。
  • 「零边际成本」有边界。 仅对已持有 128GB 机器者成立；团队推广 = 每人硬件或共享服务器（单流吞吐瓶颈）。提案措辞必须是「隐私敏感 + 个人编辑」补充档，不可写「替代云端」。
  • 结论时效。 Qwen3.8 谱系 + 早期 fork 生态，六个月后可能面目全非；长期资产是评测框架，而非单次结论。

Proposal D｜Qoder 试点成本模型补上「cache 命中率 + compaction 开销」两个隐藏维度

依据：omp-jev-compaction 源码亲测 + 16,198 条真实消息回放数据。数字经工具核算，示意计算基于主流 provider 公开定价结构（input=1.0x、cache write=1.25x、cache read=0.1x、output=4x）。

1｜核心主张（一句话）

按「订阅单价 × token 量」对比工具成本，在长 agent 会话真实负载下结论可能整体反转——同量 token 因 cache 命中与 compaction 桶结构不同，成本差实测可达 1.7-7.8 倍；补上这两个维度约 3 人日，且只有试点窗口内拿得到真实分桶数据。

经得起追问的底气：40 请求 × 100k prefix 场景——sticky 复用 515 单位 vs 决策式重写 860（+67%）vs LLM 总结式 1280（+149%）vs 无缓存 4000（+680%）。单价×总量模型对此完全不可见。

3｜成本模型 v2（单维 → 结构化）

v0（现状）：成本 = 订阅单价 + 模型预算估算
v2（提案）：会话成本 = 订阅分摊 + Σ(token桶 × 桶单价)
           桶 = cache_write(1.25x) | cache_read(0.1x) | miss(1.0x)
                | output(4x) | compaction重写(按实际执行者计价)

关键洞见（来自信号源亲测）：LLM 做总结按 frontier 价收 input+output；决策模型做 compaction 输入 $0.042-0.20/MTok、输出免费（「too cheap to meter」）。compaction 策略本身就是定价结构。实测 sticky 模式 40 请求仅 3 次 rewrite、0 次 prefix break——这正是「工具便宜」表象下看不见的杠杆。

0. 定位：与 09-18 推荐重排提案的分野

「typed decision 便宜、快、结构化」已是 09-18 提案论证过的既定事实，本文不再重复。本文押的是同一架构判断在不同场景的差异化赌注——Life OS 是决策层最快、最便宜的证伪场：

维度 企业重排场景（09-18） Life OS 场景（本提案）
合规/数据 须自托管 OpenJev 单用户直连 Jev API 即可
负载/成本 主链路 QPS，成本敏感 百次/天量级，月成本个位数美元
问题集 须冻结评测集、防漂移 自产——触发规则本来在自己手里

两份互为期权：此处 3 天可证伪的结论（问题集设计、校准方法、阈值路由经验），直接决定彼处 1 人月投入该不该花。

1. 核心主张

主动式 agent 卡在每日级，不是 LLM 不够聪明，而是让 System 2 干了 System 1 的活——把「该不该行动」（decision）交给 typed decision model 做 ~100ms 结构化判断，LLM 只做放行后的「怎么做」（generation）；Life OS 无合规与评测集约束，可在两周内以个位数美元完成证伪或证实。

三个可追问的支点：

  1. 决策≠生成。「该不该提醒」是判别问题，不是生成问题；判别交给生成模型 = 杀鸡用牛刀且刀钝（延迟/幻觉/成本）。分层有先例：人脑双系统、传统软件 if-else vs ML。
  2. 工程模式已亲测可用（fast-jev-compaction 源码）：typed question + 阈值路由（keepThreshold）+ 分片并发 + 失败显式 throw——拿来即用，非纸面推理。
  3. 本场景独有的低门槛：问题集自产、单用户负载、无合规摩擦——证伪回路全链路短于任何企业场景。

2. 锁定痛点

Life OS 的 Proactive Agents 需要高频、低成本、可信赖的决策原语，今天只有两个坏选项：

场景 今日实现 痛点
简报触发（每日阅读简报） 固定 cron 时间错配：忙时推、闲时空
提醒时机（1:1/会议准备） 硬编码「提前 30 分钟」 无视深度工作/正在会议中
Inbox 分诊（新到内容） 夜间整批处理 「这条值得插队吗」无处安放

共性：都是「该不该打扰用户」的高频小决策。硬编码 = 决策质量差；LLM = 1,440 次/天 × $0.0075/次 ≈ $10.8/天且秒级延迟，皆不可行。结果：agent 只能降级为每日定时任务，系统永远「事后」而非「适时」。

3. 架构

信号（分钟级）──► 决策层 System 1：Jev / 规则（~100ms，typed answer + 置信度）
                    ├─ 高置信 → 执行 / 静默
                    └─ 低置信 → 升级 ──► 生成层 System 2：LLM（秒级）──► 动作
审计：决策 JSONL ──► Trust & Eval 支柱复用
协议：typed decision 消息类型 ──► agent 通信项目（与 E2E 加密正交）

agent 架构正浮现三层标准分层：生成层（LLM）+ 决策层（typed model）+ 通信层（agent 间消息）。手头两个项目恰好覆盖后两层——不是追热点，是拼图自然补齐。

9. 诚实挑战

问一：规则引擎/传统 ML 是不是早就够了？ 部分成立。「会议中勿扰」= 日历查询；「晨间简报」= 时间规则——估计 70% 的高频决策可由规则覆盖，且更快更免费。typed model 只对「模糊带」有价值：语义判断、且规则补丁维护成本高的部分（如「这篇内容值得此刻插队吗」）。对策已内建于 M1：网关第一适配器就是规则 baseline，Jev 只接管规则不确定的案例。自省一问：上次因维护 if-else 而痛苦是何时？答不出，需求存疑。

问二：「新范式」是不是营销包装？ 半成立。typed output + 置信度不新——function calling / Pydantic / 概率输出几十年了；唯一新的「非生成架构砍掉延迟与成本数量级」，clones 已号称 38ms，这点差异也快被抹平。结论：这不是范式革命，是决策层商品化——恰因商品化，价值不在选型（Jev vs OpenJev），在自产 question set 与 audit 数据。另戳一点：「结构性防幻觉」≠ 答案正确，typed 错误仍是错误，只是错得结构化；校准之前，「可信赖」是愿景不是事实。

问三：agent 真需要分钟级决策吗？还是在为不存在的需求设计？ 最狠一问。动作空间本身低频（简报日推 1 次即满）时，「正确时刻」大多可事件驱动达成——解锁屏幕、日历空档、新消息到达——事件触发 + 规则或已足够，无需轮询任何模型。三连判据：①列出 3 个「晚 1 小时发现就亏」的场景；②列出 1 个事件驱动覆盖不了的时机判断；③记录两周内真实「错过的时机」。三项皆空 → 弃分钟级，留网关 + 规则。North star 是打扰的准与不准（时机精确率），决策频率只是手段——为频率而频率是指标陷阱。

问四：止损条件是什么？（正面回应 09-18 的硬止损） 09-18 企业重排提案：1 人月上限、5-6 周期权定位。本提案场景证伪成本更低，故条款更细也更狠：

止损维度 条款
时间 单点实验 ≤3 个人日；两周无正信号即弃
金钱 API 费用 <$10（单用户百次/天，天然封顶）
门 A（M0 后） 一致率 >98% 且分歧皆琐碎 → 规则已够，弃 Jev
门 B（M2 后） 模糊带 <10% 流量 → 弃模型，只留网关接口
门 C（随时） 问三三连判据皆空 → 弃分钟级方向本身
纪律 门 A/B 未过，禁一切平台化投入

低成本的反面是注意力涣散——「失败即弃、不做平台」是对冲。跑这个实验的理由恰恰是它便宜到没有理由不跑，狠到跑错立刻死。
