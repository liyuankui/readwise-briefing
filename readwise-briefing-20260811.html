② Shopify 用 MySQL SKIP LOCKED 替代 Redis 做库存预留

来源：HN 2026-08-10 → Shopify Engineering 原文 · HN 讨论

核心信号：Shopify 把 checkout 防超卖逻辑从 Redis 迁回 MySQL，关键设计："一行一个可售单位" + SELECT ... FOR UPDATE SKIP LOCKED。验证支撑了 Black Friday $5.1M/min 峰值（writer CPU <50%, reader CPU <16%）。

关键工程细节（已读原文）：

  • 为何迁回：Redis（预留）+ MySQL（库存台账）双系统无法原子写入 → 超卖/欠卖风险；统一到 MySQL 拿回 ACID + 多仓感知。
  • SKIP LOCKED 的价值：并发事务跳过被锁行直接取可用行，不互相阻塞 → 高吞吐低争用。
  • 一行一单位：不用 quantity 列，每个可售单位独占一行；池子上限 1000/品/仓，耗尽时单事务内 inline 补货（防惊群）。
  • 踩坑：REPEATABLE READ 下 gap lock（含 supremum）阻塞补货 → 死锁；改 READ COMMITTED 解决。自增主键导致双索引双锁 → 换复合主键减半锁足迹。
  • 反教训："瓶颈不在预期处"——优化数周后发现真正天花板是 checkout 链路里无关代码的连接耗尽。

验证结论：✅ Verified — Shopify Engineering 官方博客，HN/Reddit/LinkedIn 多源印证，含具体性能数字。

🎯 为什么与你高度相关：
· 你的本职是 IKEA Order 生命周期 + 库存/物流，checkout→order→delivery 的库存预留是核心场景；Shopify 的"防超卖 + 高并发"与 MPC 交易链路同构。
· Store POS Modernization Phase 2 的 Cart 计价 + C&C 订单正需要库存一致性保障——SKIP LOCKED 是比 Redis/Lua 脚本更简单、更可观测的选项（你的栈以 PostgreSQL/MySQL 为主）。
· gap lock / READ COMMITTED / 复合主键 三连是经典踩坑序列，可直接进 Engineering Baseline 的"高并发库存"知识库，喂给团队 AI Coding Eval 的真实 case。
