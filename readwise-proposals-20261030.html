P1 · 「Agent 工具网关」三线合流设计参考

可学的不是网关本体，而是治理机制

信号：Uber MCP Gateway（✅ 转述）× Salesforce 精选铁律 × Shopify verify 原则 · 连接：opencode F2-F5 / Agent 沙箱 / eval 线
Uber 网关可学三机制：自动发现、默认禁用+审批、按会话授权——11 人团队借机制不借架构，与三条在途线合流。

① 矛盾统一：静态精选 vs 动态治理

Salesforce（人工精选，窄而高信噪比）与 Uber（AutoCrawler 广发现 + 默认禁用严管控）不冲突，是「发现广度 × 治理强度」两端。落地：评估框架新增评分项工具治理成熟度——L1 有清单 → L2 默认禁用+审批 → L3 会话级授权（衔接沙箱线）→ L4 IDL 自动发现。并入 F2-F5。

② verify 入口网关化

Shopify 原则升级：*_verify 注册为 Registry 标准工具类别，agent 可自验证调用结果——与 SentinelOne recovery、eval 线闭环：eval 失败 → 自动调 verify → 恢复或上报，不等人。

③ 最小落地：清单文件 + CI（<100 行）

不做控制面/数据面分离，只借两个机制：自动发现 → 脚本从 OpenAPI/SKILL.md 生成 tools.yaml（名称/owner/默认禁用/PII 标记/verify 类别）；默认禁用+审批 → CI 检查（未登记或未审批即 fail，审批 = PR review）。Bun+TS 实现。

里程碑与成功标准

W1 tools.yaml schema + CI 脚本 → W2 存量工具入册 → W3 verify 试点 1 服务 → W4 评分项并入 F2-F5。可测：存量工具清单覆盖率 100%；未审批新工具 CI 拦截率 100%；试点服务 agent 自验证成功率 ≥80%；≥10 个工具完成治理评级。ROI：审批从「事后救火」变「PR 一次 review」；自验证省每次 15-30 分钟人肉排查。风险：清单流于形式（CI 强制）；默认禁用拖慢 adoption（审批 SLA 1 天）；滑向过度设计（明确不做 Proxy 网关）。

⚡ 本周三件事

  1. 定 tools.yaml schema（默认禁用/owner/verify/PII 标记）
  2. 写 CI 脚本，用 1 个反例验证拦截生效
  3. F2-F5 加「工具治理成熟度」列，评 3 个现有工具定基线

🔴 诚实挑战

  1. Uber 数千工具 vs 我们几十个：网关本体大概率过度设计——工具量不上一个量级前，不做控制面/数据面分离。
  2. ByteByteGo 转述，AutoCrawler/Omni MCP 细节以 Uber 原博为准，落地前须回源核对。
  3. 「默认禁用+审批」在 11 人互信团队可能沦为官僚动作——必须以 CI 自动化代替人工把关，否则机制空转。
