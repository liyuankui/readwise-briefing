Proposal 1 of 5
Agentic Engineering as the New Ceiling
Engineering Baseline 不是文档工程，是让下一个 AI session 比上一个更聪明的复利机制
Vibe Coding Stack Life OS Engineering Baseline 📡 信号来源: Karpathy + Sequoia AI Ascent 2026 + Learn Harness Engineerin

核心主张

Engineering Baseline 不是文档工程，是让下一个 AI session 比上一个更聪明的复利机制。

锁定的具体痛点

Order 团队 Java 工程师每次 agent session 花 30–45 分钟重建上下文，这就是复利的反面。

实施里程碑

  • M1 · 本周痛点量化：统计 3 名工程师的 session 重建时间（问卷或观察）
  • M2 · 2周内五机制 Harness 落地：指令/状态/验证/范围/会话，每个机制指定负责人
  • M3 · 4周内机器可读 AGENTS.md 模板推广到全团队（Java + Golang 双版本）
  • M4 · 6周内确定性验证：CI 自动检查 AGENTS.md 存在且完整
  • M5 · 8周内第一次复利验证：对比前后 session 启动时间，数字说话

成功标准（可测量）

  • Session 重建时间从 30-45 分钟降至 <10 分钟
  • 11 名工程师 100% 有机器可读 AGENTS.md
  • CI pipeline 覆盖 Harness 完整性检查
  • 下一轮 agent session 可直接接续上一轮，不丢失上下文

ROI / 业务影响

按 11 人 × 20 分钟/天 × 250天/年 = 916 小时/年。按工程师时薪 200 RMB，= 18.3 万 RMB/年可回收的时间成本。

风险与缓解

⚠️ 团队抵触：'这不是新东西'→ 强调这是 AI 时代的新基础设施，不是传统文档
⚠️ 覆盖率目标可能错误→ 先用 3 名志愿者验证框架，再全员推广
⚠️ Harness 维护成本→ 把 Harness 更新纳入 PR checklist，自动提醒

立即行动（本周内）

  • ①本周内统计 3 名工程师 session 重建时间（建立 baseline）
  • ②阅读 Learn Harness Engineering 课程，提炼五机制模板
  • ③把 grapeot 的复利系统框架发给团队周会讨论

🔴 诚实挑战（主动找漏洞）

这不是新东西——AGENTS.md 已存在，问题是没人更新它。工具不够，需要文化变革。
覆盖率目标（11人100%）可能误导——低质量 AGENTS.md 比没有更糟糕，质量比数量重要。
Proposal 2 of 5
GEO 专项论文 → IKEA 追踪框架
AI 引用偏好正在 2026 年固化，IKEA 的窗口期是未来 3 个月
GEO for IKEA 📡 信号来源: 姚金刚 GEO 全球第二篇专项论文（602 prompts × 21143 引用 × 23745 AI抓取记录）

核心主张

AI 引用偏好正在 2026 年固化，IKEA 的窗口期是未来 3 个月——5/31 前必须有 IKEA 引用率的第一个数字。

锁定的具体痛点

IKEA China 不知道自己在豆包/元宝/Kimi/千问/DeepSeek 上的引用率是多少，更不知道宝尊运营内容是否在被 AI 索引。

实施里程碑

  • M1 · 本周完善 Prompt 库：参考论文 602 条框架，设计 IKEA 版 75 条（5品类×3意图×5平台）
  • M2 · W19执行首轮收纳品类盲测（5个平台 × 15条 prompts），记录 IKEA 引用率
  • M3 · W20分析引用模式：IKEA 在哪些场景被引用/被忽略，对比竞品（宜家中文表达 vs IKEA）
  • M4 · W21扩展到全部 5 品类，完成基线审计
  • M5 · 5/31交付给 Roman/Maggie：基线审计报告 + 追踪框架方案（哪怕 IKEA 引用率是 0%）

成功标准（可测量）

  • 5/31 前有 IKEA 在 5 个国内 AI 平台的引用率具体数字
  • 至少 75 条 prompts 有测试记录
  • 识别出至少 2 个 IKEA 引用盲区（品类 or 平台）
  • 产出可重复执行的追踪框架（不是一次性测试）

ROI / 业务影响

GEO 先动者优势：AI 搜索引擎引用逻辑固化后，补救成本是预防成本的 10 倍。IKEA China 年 GMV 数十亿，每提升 1% AI 引用率对应的品牌曝光价值保守估计数百万 RMB。

风险与缓解

⚠️ 没有 stakeholder 买单→ 把 GEO 嵌入宝尊报告，不作为独立项目，借力 Roman 的 5/31 deadline
⚠️ 时间线理想化→ M1-M2 可以在 1 周内完成，关键是立即启动
⚠️ 执行权在内容团队不在 CDH→ Kyle 只负责框架和数据，内容改造推给酒令团队

立即行动（本周内）

  • ①联系姚金刚获取 GEO 论文全文（Twitter: @yaojingang），复用 602 prompts 设计框架
  • ②本周执行首轮收纳品类盲测（5个平台 × 5条 prompts = 25次测试，2小时内完成）
  • ③给酒令团队发邮件，把 GEO 准备度问题加入内容模块访谈

🔴 诚实挑战（主动找漏洞）

75 条样本量置信度有限——论文用 602 条才得到统计显著结论，75 条只是方向性参考。
中文 AI 平台引用逻辑不透明——豆包等不开放 API，只能人工测试，可重复性存疑。
CDH 是工程团队，内容改造不在职责范围内——框架建好后推进需要跨团队协作，存在阻力。
Proposal 3 of 5
Implementation Science for AI Adoption
AI 采纳失败从不是工具问题，而是迁移失败问题——讲师团的真正使命是让新行为在没有讲师的情况下也能存活
AI Upskill Trainer AI Adoption Strategy 📡 信号来源: @rwayne - Implementation Science + @HiTw93 - 非技术同学AI Coding基

核心主张

AI 采纳失败从不是工具问题，而是迁移失败问题——CDH 讲师团的真正使命，是将新行为从培训室迁移到业务现场，并让它在没有讲师的情况下也能存活。

锁定的具体痛点

一个非技术业务用户参加 L0 培训后，回到岗位第一天就回退到旧习惯——不是她不想用 AI，是工作环境没有提示她用、没有让她成功的脚手架、没有同伴压力。

实施里程碑

  • M1 · 本周在讲师团大纲中加入 Implementation Science 模块（为什么迁移失败的5大原因）
  • M2 · W19-20为每期培训设计'30天行为追踪'：3个可观察的目标行为，每周打卡
  • M3 · W21第一期培训加入环境脚手架：给参与者配置好 Copilot CLI + Notebooks 工作环境
  • M4 · W22-23引入同伴学习小组（3-4人）：互相问责，替代讲师持续陪跑
  • M5 · W2430天后测量行为改变率（不是满意度），报告给 Nicole

成功标准（可测量）

  • 30天行为追踪：70%+ 参与者保持至少 1 个目标行为（可观察，非自评）
  • 回退率 <30%（培训后 2 周仍在用 AI 工具的比例）
  • 每期培训产出至少 1 个'内部传播者'（能自发向同事介绍工具的人）
  • 不用满意度问卷衡量——用工具使用率数据（PostHog 或日志）

ROI / 业务影响

29人调研显示高意愿·低方法论。1个有效传播者 = 带动3-5人。11名 CDH 工程师中有 5 名讲师 = 潜在影响 15-25 名业务用户/期。

风险与缓解

⚠️ Implementation Science 对 IKEA 文化太学术→ 只用概念，不说名词：'我们要确保培训效果持续到工作现场'
⚠️ 行为追踪引发隐私顾虑→ 用自愿打卡，不用强制监控；数据聚合不显示个人
⚠️ 讲师团本身缺人（P0缺口）→ 先用现有资源跑 1 期 pilot，边跑边招

立即行动（本周内）

  • ①在讲师团大纲中加入一个新章节：为什么培训后会回退（5大原因 + 解法）
  • ②设计 3 个可观察的目标行为清单（培训后第 1/7/30 天各检查一次）
  • ③调研 Implementation Science 入门材料（Fixsen 2005 框架 + Greenhalgh 2004 扩散理论）

🔴 诚实挑战（主动找漏洞）

Implementation Science 本身在中国企业文化中适用性存疑——它诞生于西方教育/公共卫生领域，IKEA 的科层结构可能覆盖它的作用机制。
Kyle 是工程师管理者，不是学习设计师——Implementation Science 需要专业 L&D 背景，不能只是贴标签。
30天追踪可能测量的是'有时间用'而非'真的采纳'——业务压力期会让数据失真。
Proposal 4 of 5
元Skill 架构设计
用工程化 Meta-Skill 把写出一个能用的 Skill 从两天砍到两小时，且生成物天然具备可测、可控的工程边界
IKEA Skill Hub Life OS Skills Development 📡 信号来源: @yaojingang 元Skill + @lencx_ Codex Pet Skill 解析 + Waza v3.11

核心主张

用一个工程化 Meta-Skill，把写出一个能用的 Skill 从两天砍到两小时，且生成物天然具备可测、可控的工程边界。

锁定的具体痛点

一名 IKEA CDH 工程师想创建一个 Skill，他看了 SKILL.md 模板后不知道从哪里开始，写出来的 Skill 是角色扮演而非工程边界控制——2天后放弃。

实施里程碑

  • M0 · 本周扫描现有 51 个 Skills，量化角色扮演比例（grep 角色/扮演/你是 等关键词）
  • M1 · 2周内设计 Meta-Skill SKILL.md 骨架：五步流水线 DIAGNOSE→INTERROGATE→SCAFFOLD→VALIDATE→PACKAGE
  • M2 · 4周内实现 validate.ts (Bun + TypeScript)：12条可机器检查的工程边界规则
  • M3 · 6周内4种 Skill 类型模板：Workflow / Tool-Wrapper / Domain-Expert / Pipeline（禁 Persona）
  • M4 · 8周内找 1 名工程师用 Meta-Skill 创建新 Skill，计时，目标 <2 小时

成功标准（可测量）

  • 新创建的 Skills 通过 validate.ts 的合格率 >90%
  • 角色扮演型 Skill 比例从当前水平降至 <10%
  • 新 Skill 创建时间从 2天 降至 <2小时
  • Meta-Skill 本身能被 validate.ts 验证（自引用测试）

ROI / 业务影响

IKEA Skill Hub 当前 51 个 Skills，目标接入更多仓库（ODI/Platform/Global）。Meta-Skill 是规模化的前提——没有质量门禁，Skills 越多越乱。

风险与缓解

⚠️ Meta-Skill 降低供给门槛，但不解决贡献激励问题→ 需要管理动作（1:1 OKR）配合，不是工具能解决的
⚠️ 12条规则可能过于严格→ 分 fatal/warning 两级，fatal 才阻断，warning 只提示
⚠️ Bun + TypeScript 依赖→ validate.ts 保持零外部依赖，只用 Bun 内置功能

立即行动（本周内）

  • ①grep 扫描现有 51 个 Skills，量化角色扮演比例（建立改造 baseline）
  • ②找 1 名从未写过 Skill 的工程师，计时测试创建过程（暴露真实卡点）
  • ③写 Meta-Skill SKILL.md 骨架 M0 草案（3天内）

🔴 诚实挑战（主动找漏洞）

Meta-Skill 是工具问题的解法，但工程师不主动贡献是激励问题——工具再好也无法替代管理动作。
五步流水线可能让简单 Skill 过度工程化——需要设计 fast track（简单场景 2步完成）。
validate.ts 12条规则是我设计的，缺乏实战验证——第一批 Skills 需要人工 review 对照，规则可能需要大幅调整。
Proposal 5 of 5
Agent 经济 → 宝尊能力边界新判断
Agent Economy 信号把替代宝尊的瓶颈，从 AI够不够聪明 移到了 IKEA能不能拿到平台操作授权
宝尊运营 Ontology 📡 信号来源: Stripe Agent Link + Agent Vault + 硅谷10人干100人活

核心主张

Agent Economy 信号把替代宝尊的瓶颈，从 AI 够不够聪明 移到了 IKEA 能不能拿到平台操作授权——这让商品管理域（KK）的优先级从次高升为最高。

锁定的具体痛点

团队在分析哪些宝尊运营可以被 AI 替代，但分析框架是错的：不是问 AI 能不能做，而是问 IKEA 有没有权限让 AI 做——天猫 API 授权才是真正的瓶颈。

实施里程碑

  • M1 · 本周约 KK 30分钟访谈：重点问商品操作的授权链路（谁有权改商品信息？授权路径是什么？）
  • M2 · W19查阅天猫/JD Open Platform 文档：独立验证 API 可达性，建立授权能力地图
  • M3 · W20给 Roman 发短邮件：明确 5/31 里程碑类型（是决策建议 or 技术 PoC？）
  • M4 · W21完成商品域授权-能力矩阵：哪些操作可API化 / 哪些需人工审批 / 哪些平台封锁
  • M5 · 5/31交付给 Roman：宝尊运营替代的优先级排序 + 授权瓶颈分析（不只是 AI 能力分析）

成功标准（可测量）

  • 产出授权-能力矩阵（覆盖售后/商品/内容/投流四域）
  • 明确至少 3 个 IKEA 当前有权调用的 API 操作（商品域重点）
  • 识别至少 1 个真正的零阻力替代点（授权 + AI 能力双就绪）
  • 5/31 交付 Roman 可行动的优先级建议，不是技术概念报告

ROI / 业务影响

宝尊运营成本数千万 RMB/年。即使只替代 20% 的操作，年节省保守估计数百万。但更重要的是：找到正确的瓶颈（授权而非 AI 能力），避免在错误方向浪费 3 个月。

风险与缓解

⚠️ Stripe Agent Link 在中国基本失效→ 落地形式是规则化 RPA + 人工审批节点，非真正 Agent 授权——但逻辑不变
⚠️ 天猫/JD API 授权申请周期长→ 先做 API 可达性调研，再决定是否申请——不要先假设可以申请
⚠️ Agent Vault 安全模式在国内无直接替代→ 用权限最小化原则替代：IKEA 的 Agent 只拿只读权限，写权限须人工二次确认

立即行动（本周内）

  • ①约 KK 30分钟：重点问商品操作授权链路（本周内）
  • ②给 Roman 发短邮件：5/31 的里程碑是什么类型？（2分钟内）
  • ③查阅天猫 Open Platform 文档，建立商品域 API 能力清单（半天内）

🔴 诚实挑战（主动找漏洞）

Stripe Agent Wallet 逻辑在中国基本失效——天猫/JD 是封闭生态，实际落地是 RPA 而非 Agent 授权，信号的适用性有限。
这个 Proposal 把瓶颈从 AI 能力移到授权，但两者可能同时存在——不能用新框架完全替代旧分析。
KK 访谈和平台 API 调研是 Kyle 能控制的，但最终决策在 Roman——5/31 交付物的影响力取决于 Roman 的决策权限。
