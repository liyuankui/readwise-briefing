11-04 · lethain.com（Will Larson——small-change 作者再现）

要求每个 PR 生成 verifications/{pr_num}.md：记录已验证步骤与未能验证之处。五步循环：实现 → 带验证文件开 PR → ai-code-review + 人工反馈 → 采纳或 /dismiss{reason} 拒绝 → 每日更新技能与工具。复查验证文件找缺口收紧指导。效果：「improving our codebase's correctness while we sleep」（每早 4-6 待审 PR）。关键概念：重复指导 = context poison（应沉淀为工具/模板而非反复说）。

⭐×4 Anthropic 重造源码控制（已回源）

Scion：无 push 的服务端 Git✅ 全文已读

11-04 · ByteByteGo（二手转述）

抛弃 Git 客户端中心模式：服务端承担历史查询/diff/提交/合并，客户端只留轻缓存。changeset 内容寻址不可变（元数据存 Spanner、内容存对象存储）；三层缓存逐级取缺。量化：日合并 3 万+、CI 检出 2500 万次/日（否则 600PB+/天流量）；7 人小团队建成 Scion + 评审工具 Antique。

「验证基础设施」系列的极端样本：当 CI 检出量达到千万级/日，源码控制本身成为瓶颈——Anthropic 选择重造而非优化。对我们的启示不在工具（我们远未到此规模），而在「7 人团队重造核心基础设施」的可行性边界——与零 Rust 重构同一叙事：小团队 + AI = 以前不可能的工程。原文
