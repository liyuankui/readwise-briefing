#1Software Factory v0.1✅ ✅

Proposal #1 — Software Factory v0.1：autodev → autoreview → autoissue 三件套

信号：@fengxia17063046（OwlWorks）autoissue/autodev/autoreview 工程实践 · 验证 ✅ Verified 对齐：Life OS — Software Factory · F12 Intent-to-Delivery 闭环 · 终局类型 CREATE

1. 核心主张

在 Kyle 的 Notebooks 仓库（private）落三件套，用一个真实 issue 走完”拆需求→开分支→写代码→提PR→AI review→合并”全闭环；先个人仓库验证，再决定是否进 IKEA GHES。

2. 锁定痛点

痛点不在单步，在编排：Kyle 手动改一个文件要 7 步（想拆法→开分支→改→add/commit→gh pr create→@copilot review→gh pr merge），其中 6 步已有 skill（commit/pr-helper/ikea-github），但每次都要他当调度员串联。SEM 时间最低效用法。基线（待实测）：~7.5-9.5h/月。

3. 里程碑（诚实重排后）

M 内容 时间
M1 autodev（最该先做）：检索 open issue→排优→开分支→改→commit→建 PR 2 周
M2 autoreview：PR 创建后触发 Copilot review→解析→通过则通知 Kyle 手动 merge（不自动合并，R8 硬规则） 1 周
M3 autoissue：一句话意图→结构化 issue→提交 1 周
M4 度量 + notebooks-dashboard “Software Factory” tab 1 周

4. 成功标准（可测量）

  • issue→merged PR 全自动 ≥3 个/月
  • Kyle 介入率 ≤2 步/PR
  • 月省时间 ≥6h
  • autodev PR 被 review 一次通过率 ≥60%
  • 越界改动（碰 intent/journal/SKILL.md）= 0

失败止损：M1 结束若一次通过率 <30%，回炉而非进 M2。

5. ROI

直接：月省 6-8h（~9000-12000 RMB），2-3 月回本。战略：证伪 Software Factory 假设（notebooks 跑不通就别进 GHES）；团队示范（SEM 自己用 Agent 跑 PR 比”AI 推广会”管用）。

6. 风险与缓解

风险 缓解
改坏 SKILL.md/intent pre-commit hook 拒越界 path；M1 dry-run 一周
SSH key 复杂（liyuankui 仓库需 id_rsa_liyuankui@gmail.com） autodev 调 sd git gmail，M1 第一天验证
成本失控（claude -p 反复调） 每 issue token 预算 50k，超限转人工
过早进 GHES 合规出事 本 proposal 显式不进 GHES；进需独立 proposal + security review

7. 立即行动（本周）

  1. 验证 SSH+gh（30min，最大未知数）：sd git gmail "git fetch" + gh auth status + gh issue list 确认 notebooks 可被 Agent 操作。
  2. 手动模拟 autoissue dry-run：输入”修 ira-best-practices 与 IRA_FRAMEWORK 矛盾”→看拆解质量。
  3. notebooks-dashboard 加空白 “Software Factory” tab（可视化是最强动力锚）。

8. 诚实挑战

  • 落地顺序错了：信号源说 autoissue 先，但 Kyle 真实瓶颈是写代码+串 PR，应 autodev 先。已重排里程碑。
  • autoissue 最难进 IKEA（GHES issue 关联 Jira、traceability、webhook 污染）；最容易进 IKEA 的是 autoreview（只读+评论）。
  • autodev 自动合并在 IKEA 企业仓库必违规（branch protection/SOX/变更管理）——所以 M2 只通知不合并。
  • 7.5h/月 基线是类比非实测：Action 1 前先 git log --since="2 months" --author=liyuankui --oneline|wc -l，若 notebooks commit <10 次/月，降级为”先在 GHES 低风险内部仓库试点”。
  • 与 F12 重叠：F12 是 SPEC 规划中未动；本 proposal 是把它砍到 CREATE 终局 + notebooks 作先导实验，跑通 F12 复用 80%。

相关文件：workspace/life-os/SPEC.md(F12)、PROPOSAL_FIRST_PROACTIVE_AGENT.md；可复用 skill：ikea-github/pr-helper/commit/gemini-code-assist-manager。

#2Code Review 人机边界重构⚠️ ⚠️
Eng Baseline · 守门人分诊制

Proposal #2 — Code Review 人机边界重构（守门人分诊制）

信号：@Xudong07452910「人工 Code Review 该淘汰」 · 验证 ⚠️ 框架被工业反驳，趋势真 对齐：Engineering Baseline & Tech Debt · 终局类型 SYSTEM

1. 核心主张

不在”废不废人工 review”，而在分诊：AI 守”机械正确性门”（lint/bug/安全/测试覆盖），人守”语义正确性门”（架构一致性、知识传播、边界判断）——把 SEM 从 nitpick 里解放，专注只有人能做的判断。

2. 锁定痛点

场景一人：Kyle 作为 SEM 同时是团队 review 瓶颈。PR 排队等他，而他 80% review 时间花在”这命名规范吗/有测试吗/空指针吗”——这些是确定性规则，AI 比人快且不累。真正需要他的（“这个抽象合理吗”“会影响 POS 计价链路吗”“新人能看懂吗”）反而被挤压。 - 量化基线（待 Action 1 实测）：假设团队 11 人 × 每周 3 PR × review 占 Kyle 15min → ~8h/周被机械 review 吞掉。

3. 里程碑

M 内容 时间
M1 试点：选 1 个低风险 GHES 仓库，接 Copilot/Gemini Code Assist 跑 AI 首轮 review 1 周
M2 立《人机 review 分工清单》：明确哪些 AI 全权（lint/format/obvious bug）、哪些人必审（架构/跨服务影响/安全敏感） 1 周
M3 改 PR 模板：AI review 通过后 PR 才进人审队列；人审只标”语义问题” 1 周
M4 度量推广：扩到团队 3 个仓库 持续

4. 成功标准（可测量）

  • review 周期（PR 创建→合并）中位数 ↓ 40%
  • Kyle 人审平均耗时/PR ↓ 60%（从 15min→6min）
  • 知识传播指标不降：人审中”提问/讨论”评论占比 ≥ 维持基线（防 AI 削弱传播）
  • 缺陷逃逸率（合并后 prod bug）持平或↓

5. ROI

直接：Kyle 月省 ~30h 机械 review → 投入架构/1:1/战略。战略：为”AI Coding 推广”提供可信工程实践（不是 demo，是制度）。

6. 风险与缓解

风险 缓解
知识传播被削弱（AI 替掉新人被 review 的学习机会） 人审保留”为什么这么改”问答；M2 清单显式把”教学性 review”划给人
AI review 噪音（无意义 comment） 只处理 severity≥major；minor 汇总一条
IKEA 内网合规（Code Assist 走外网？） 用 GHES 内置 reviewer 或内网模型；R9 边界内

7. 立即行动（本周）

  1. 实测基线：gh pr list 统计近 1 月团队 PR 的 review 周期 + 抽样 10 个 PR 看人审评论里多少是机械问题。
  2. 找 1 个 volunteer 仓库试点 Copilot review，对比 AI 前/后人审耗时。
  3. 起草《人机 review 分工清单》v0.1 草案（半页）。

8. 诚实挑战

  • “AI 增强后人会更懒”：若人审变成橡皮图章，知识传播实际会降。缓解靠 M2 清单 + 把”提问”写进 PR 模板强制项。
  • 8h/周 基线是假设：若实测团队 PR 大多互审（不经 Kyle），ROI 就不成立，应降级为”帮工程师互审提效”而非”解放 SEM”。
  • IKEA 合规：自动 reviewer 在生产仓库可能触发变更管理审计问题，试点必须低风险仓库 + 先问 security。
  • kepano 反向风险：“your edge is what models don’t know”——人的价值在隐性判断，若把 review 机械化的同时没强化语义判断，就是把人的 edge 也让渡了。
#3多智能体编排：先做模式⚠️ ⚠️
Life OS · orchestrator-worker

Proposal #3 — 多智能体编排：先做”编排模式”，不上 Swarm 框架

信号：@Phoenixyin13「Agent Swarm / Omnigent」 · 验证 ⚠️ Omnigent 产品未验证，编排趋势确证 对齐：Life OS · Proactive Agents · 终局类型 SYSTEM

1. 核心主张

别绑定 Omnigent（未验证）。用 orchestrator-worker 模式，基于 Kyle 已有的 Paseo（多 agent 编排工具）+ Claude Code，先做”1 个 orchestrator + 2 个 worker”的最小协作闭环——只在单 agent context 失焦时才上多 agent。

2. 锁定痛点

场景：复杂任务单 agent 上下文失焦。本简报就是个例子——1 个 agent 要同时做”采集+验证+对齐+深挖+HTML”，context 膨胀、互相干扰。已经看到：本次 5 个 subagent 并行深挖，本质就是 orchestrator(worker=)pattern 的雏形。痛点是没有标准化的编排骨架，每次手搓。

3. 里程碑

M 内容 时间
M1 定义 orchestrator-worker 契约：orchestrator 拆任务+收结果，worker 自包含执行（已有 Paseo 做 transport） 3 天
M2 选 1 场景落地（候选：readwise-briefing 拆成 orchestrator+verifier+writer；或 system-stability 巡检 orchestrator+analyzer） 1 周
M3 加 Trust & Eval：orchestrator 对 worker 产出做验收（不盲信） 3 天
M4 决策门：度量后回答”这场景值不值多 agent”——多数任务退回单 agent 1 周

4. 成功标准

  • 试点任务：orchestrator-worker 产出质量 ≥ 单 agent（盲评）
  • 单任务成本（token/时长）≤ 单 agent × 1.5——超过即不值
  • 编排骨架可复用到第 2 个场景无需重写

5. ROI

直接有限（多 agent 更贵更慢）。战略价值在建立判断”何时该用多 agent”的准则，避免每人都手搓 + 过度工程。

6. 风险与缓解

风险 缓解
过度工程（多数任务单 agent+好 prompt 更优） M4 决策门强制做对比，不达标退单 agent
成本失控（多 worker 并行烧 token） 每 worker token 预算 + orchestrator 限并发
orchestrator 单点（它错了全错） Trust & Eval 层独立校验

7. 立即行动（本周）

  1. 写”何时用多 agent”决策清单（半页）：context 失焦？天然并行？需独立对抗验证？三条满足≥2 才上。
  2. 把 readwise-briefing 现有 5-subagent 流程文档化成 orchestrator-worker 范例（已有的实践，零新代码）。
  3. Paseo 上跑一个”1+2”玩具闭环，验证 transport 契约。

8. 诚实挑战

  • 最大风险是自我合理化：Kyle 在搞 Life OS，容易把”多 agent”当目标而非手段。诚实问：本次 5 subagent 真的比”我顺序写 5 个 proposal”质量高吗？——529 失败证明编排稳定性本身是成本。
  • Omnigent 是营销：验证已证伪，提案不应引用它作依据。多 agent 编排的真实信源是 Metaswarm、Zaharia OSS、orchestrator-worker 论文。
  • Paseo 已在用了：是否重复造？——不重复，是把”已经在用的模式”固化成可复用骨架。
  • KISS：若 M4 显示 80% 场景单 agent 更优，这个 proposal 的产出就是一份”别用多 agent”的决策文档，那也是成功。
#4AI Starter Kit 升级✅ ✅
AI Starter Kit · 交付工作流模板

Proposal #4 — AI Starter Kit 升级：交付”工作流模板”而非”工具安装”

信号：@sitinme「把 Claude Code 配置成可重复、可验证、能协作的工程工作流」 · 验证 ✅ Verified 对齐：AI Starter Kit + Engineering Baseline · 终局类型 COLLABORATE/CREATE

1. 核心主张

AI Starter Kit 的核心交付物从”一键装工具链”升级为”一键装可复用工程工作流模板”——让新同事装完后第一次打开 Claude Code 就在工作流里，而不是面对一个更聪明的聊天窗口。工具会过时，工作流（可重复·可验证·协作）是工程资产。

2. 锁定痛点

场景：新同事按 Starter Kit 装好 Claude Code + 登录，然后……不知道干嘛。他用”聊天窗口模式”：问一句→生成代码→复制→改→报错→再问。问题不在工具没装好，在没有把”工程流程”也装进去——没有标准 CLAUDE.md、没有 skill 包、没有”改完怎么验证”的约定。结果：工具到位，生产力没到位，AI Coding 采纳卡在”会用但用不好”。

3. 里程碑

M 内容 时间
M1 定义”标准工作流模板”：仓库级 CLAUDE.md + commit/PR 规约 + 验证 checklist 1 周
M2 打包 skill 子集（commit/pr-helper/ikea-github 等通用件）成 Starter Kit 可选装 1 周
M3 写”工作流示例”：1 个 Java、1 个 Golang 端到端范例（改→测→PR），新同事照着跑通 1 周
M4 度量采纳：新同事首次独立完成 PR 的时间、skill 复用率 持续

4. 成功标准（可测量）

  • 新同事从装 Kit 到首次独立提交合格 PR 的中位时间 ↓ 50%
  • 安装后 2 周内 skill 复用率（至少用 ≥2 个 skill）≥ 70%
  • 团队 PR 描述/测试规范一致性 ↑（可 lint）

5. ROI / 采纳影响

直接：缩短新人 ramp-up。战略：把”AI Coding 推广”从”教工具”升维到”教流程”——流程才是 Engineering Baseline 的载体，也是团队一致性（IKEA Simplicity）的杠杆。一个人用好是案例，一套模板被复用是制度。

6. 风险与缓解

风险 缓解
模板过度束缚，限制灵活性 模板分”必选/可选”层；CLAUDE.md 只写硬约束，留诠释空间
Java vs Golang 技术栈差异 M3 各做 1 个范例；模板里用条件分支而非一套硬塞
推广阻力（成员已有自己习惯） 不强制，先 volunteer 试点 + 量化对比说服

7. 立即行动（本周）

  1. 写 Starter Kit 现状盘点：当前装了什么（工具）、缺什么（流程）。半页。
  2. 起草仓库级 CLAUDE.md 模板（参考 Notebooks 自己的 AGENTS.md 分层结构）。
  3. 找 1 位近期入职同事做”5 分钟观察”：看他实际怎么用 Claude Code，验证”聊天窗口模式”假设。

8. 诚实挑战

  • “工作流模板”会变成形式主义：若 CLAUDE.md 写得太厚没人读，反而成噪音。纪律：模板 ≤ 核心规则 + 分层暴露（小模型只读 Layer 1）——Kyle 自己的 AGENTS.md 就是范例，照自己抄。
  • 栈差异是真问题：Java（Maven/ArgoCD）和 Golang（go.mod）的 build/test/部署链路完全不同，一套模板套不住，M3 必须分栈。
  • 采纳是最大变量：11 人团队推广，技术好的成员觉得模板碍事、新手又看不懂——需分层（新手用全模板，熟手用子集）。
  • 与 Proposal #1/#2 交织：本 Kit 的工作流模板里应内置人机 review 分工（#2）和 commit/PR 自动化（#1 的 autodev 单点件）——三个 proposal 是同一张工程图的不同切面，别做成三套割裂东西。
  • 诚实反问：新同事真卡在”流程”吗，还是卡在”不知道问什么”？若是后者，模板救不了，需要的是 pairing 而非文档。
#5AI 时代激发主人翁意识⚠️ ⚠️
Human Connection · 暴露问题+移除障碍

Proposal #5 — AI 时代激发主人翁意识：从”分配任务”到”暴露问题+移除障碍”

信号：@dotey 转 Felix Haas（Lovable）「主人翁意识不能分配只能靠拿」+ kepano「your edge is what models don’t know」 · 验证 ⚠️ 源未验证，共鸣强 对齐：Human Connection Investment · Engineering Baseline · 终局类型 COLLABORATE

1. 核心主张

AI 时代 SEM 的新杠杆不是”分更准的任务”，而是”暴露真实问题 + 移除障碍 + 先示弱”，让团队成员自己”看到问题直接上手”。主人翁意识无法分配，只能靠环境和示范催生——Lead by example 是 IKEA Values，也是唯一可持续路径。

2. 锁定痛点

场景：11 人团队里”等安排”现象——成员完成被分配的活，但少主动发起。Kyle（ENFJ）容易靠”我来安排/我来兜”推动，结果反而强化了”等安排”（成员知道 Kyle 会补位）。AI 进一步放大：成员把难题丢给 AI/AI agent，自己退后。这是 Human Connection 公理说的”人→Agent 替代人→人”风险。

3. 里程碑

M 内容 时间
M1 改造 1:1 结构：每周至少 1 个 1:1 不聊进度，只聊”你这周想主动拿下什么” 即刻起
M2 设”看见问题直接上手”机制：公开 backlog + 自主认领权，认领即 owner（不需 Kyle 批准） 2 周
M3 脆弱示范：双周团队会 Kyle 固定分享 1 个自己的失误/困惑（信任公理二） 即刻起
M4 度量：成员主动发起项目数、1:1 非工作话题占比、“Kyle 兜底”次数 月度

4. 成功标准（可测量）

  • 成员主动发起（非分配）项目/PR 数 ↑（月度）
  • 1:1 中成员主动提出的话题占比 ≥ 60%
  • Kyle “兜底/救火”事件数 ↓
  • 晋升 case：至少 1 名成员的主导项目可作为晋升证据

5. ROI / 团队影响

直接：Kyle 从”任务分发器”解放为”障碍清除者”。战略：团队主动性强 = IKEA Togetherness + Renew & improve 的活体证明，是团队晋升 pipeline 的根基。

6. 风险与缓解

风险 缓解
“主人翁”变甩锅借口（成员越权/产出失控） M2 认领权配”边界声明”：可见 backlog + 影响范围标签，高风险仍需 review
ENFJ Kyle 过度共情，边界模糊 M4 度量”兜底次数”作预警；定期与 Nicole/Kirill 校准
脆弱示范被误读为软弱 配”失误+我学到的+下一步”三段式，示弱不示停

7. 立即行动（本周）

  1. 本周一次 1:1 试验：完全不聊 task 进度，只问”最近什么让你兴奋/卡住”。记录反应。
  2. 把团队 backlog 公开化（issue board），加”自主认领”标签，宣布认领不需批准。
  3. 下个团队会 Kyle 先分享一个自己本周的判断失误。

8. 诚实挑战
