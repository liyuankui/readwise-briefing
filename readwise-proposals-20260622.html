工程审查契约：把一个 prompt 变成可复用的质量原语

✅ Verified 信号：@Xudong07452910 2026-06-20 关联：Testing Excellence / Upskill Trainer / Eng Baseline
核心主张：「prompt 即合同」是 AI 编码时代质量保障的最小可复制单元——一个 7 维检查清单能在零基础设施下把 review 从"看可见 bug"升级为"预防未来的坑"。这同时绕过了 8 周未动的 dual-agent proposal 的三重依赖（GHES CI/安全审查/engineer owner），并直击 Upskill Trainer #1 痛点（"怎么让 AI 听懂我"提及 5 次）。

🎯 锁定痛点

Senior Engineer 小A（ODI 团队 shoppingbff-service）：让 Copilot "review 一下这段代码"，得到 8 条全是命名/格式建议，零条触及并发竞态。两周后大促当天促销价计算错误。根因不是 Copilot 笨，是"review 一下"是没有契约的模糊指令——AI 默认产出"可见且安全的建议"。

📅 里程碑（3 周，SEM 可推动）

  • M1（第1周，4h）：契约定义 + 手动验证。交付 review-contract-v1.md（7 维 + 排序 + IKEA Java/Golang 金额/状态机/并发本地化）+ 1 份对比实验记录。go/no-go 关卡
  • M2（第1-2周，1h）：dual-agent proposal 解耦——路径 A（人工 prompt，立即可跑）vs 路径 B（CI 自动，待基础设施）
  • M3（第2周，3h）：契约泛化——deploy-checklist / dependency-upgrade / regression-test 3 个新契约，证明"prompt 即合同"是原语
  • M4（第2-3周，3h）：Upskill Trainer Track B 教学单元——3 步法（枚举维度 + 输出格式 + 否定约束）
  • M5（第3周末，2h）：效果数据 + Nicole/Kirill 1:1 汇报素材

💰 ROI

成本~13h 分散 3 周 · API <$1 · 基础设施 零
直接收益若 M1 命中 1 个未来事故（如促销价竞态），单次避损 > ¥10 万
战略收益Kyle 从 practitioner → methodologist 的关键一跃；dual-agent proposal 解冻
✅ 本周立即行动：
  1. 周二/三（2h）跑对比实验：找本周真实 PR diff，A 组"请 review 这段代码" vs B 组套 7 维契约 prompt，记录命中数。结果决定整个 proposal 生死
  2. 周四（1.5h）写 review-contract-v1.md（基于行动 1 结果）
  3. 周五（1h）更新 dual-agent proposal + 找 1 名工程师问 yes/no："这个契约你愿意下周试一次吗？"——不要群发，就找一个人
挑战 1：这是不是在给卡住的项目打补丁？→ 部分成立。但路径 A/B 解耦本身有价值。若 3 周后路径 B 仍无 owner，承认组织阻力 > 技术阻力。
挑战 2：7 维清单太"明显"？→ 旧酒装新瓶即价值——AI + 契约强制每次遍历 7 维，不依赖人纪律。但 M1 必须对比"契约 AI vs 资深人审"，不只对比"契约 AI vs 模糊 AI"。

videocut-skills 架构解剖：三个可迁移的 Skill 工程模式

⚠️ 信源已纠正 信号：@EddaMikola12279 2026-06-20（转发） 关联：IKEA Skill Hub / Upskill Trainer / Skills Dev
⚠️ 信源纠正（subagent #2 实测）：Phase 1.5 报告的 repo Ceeon/videocut-skills 有误，实际是 Agentchengfeng/chengfeng-videocut-skills（作者 chengfeng / X: @chengfeng240928 / 公众号"AI产品自由"）。这本身是教学点——信源溯源要落到仓库 AUTHORSHIP 声明，不能停在推文转发链。
核心主张：不要复制 videocut-skills，而是把它解剖成三个可迁移模式，分别灌进 IKEA Skill Hub authoring guide、Upskill Trainer L1.5 模块、和两个新 IKEA 试点 Skill——让 Kyle 现有三个项目共享同一个架构升级。

🧩 三个可迁移模式

  • ① 外置规则层（Rule Pack）：把判断逻辑从 SKILL.md 拆成编号 Markdown（1-核心原则.md / 2-语气词检测.md...），Agent 按需加载，用户可读可改
  • ② 审核页阀门（Review-Page Valve）：不可逆操作前强制生成可交互 HTML 审核页，人是阀门而非命令行确认
  • ③ 自进化闭环：纠错不写进"反馈日志"末尾，而是整合回正文规则层，越用越准

📅 里程碑

  • Phase 1（本周，Day 1-3）：模式萃取——3 份 pattern 文档（SKILL_ANATOMY 加节 + SKILL_EVOLUTION_PATTERN + REVIEW_PAGE_VALVE）
  • Phase 2（下周，Day 4-7）：Upskill Trainer L1.5"如何写好 Skill"模块，以 videocut-skills 为 Demo 解剖对象
  • Phase 3（Day 8-21）：两个试点 Skill——ikea-confluence-to-deck（Confluence→PPT）+ ikea-kpi-brief（内部 KPI 周报）

💰 ROI

Skill Hub 从"工具集市"升级为"有工艺标准的工坊"（51 skills 中仅 21.5% 五 pattern 全有）；L1.5 填补 Upskill Trainer P0 缺口里"非技术业务讲师也能教"的一环（写规则文件 < 写代码门槛）；两个试点 Skill 成为"用新模式写的示范"，带动贡献者模仿。

✅ 本周立即行动：
  1. 今天（2h）通读源头：clone Agentchengfeng/chengfeng-videocut-skills，重点读 3 处（剪口播/用户习惯/1-核心原则.md 的"❌常见错误+✅正确"对照、自进化/SKILL.md、HTML 注释"架构守护者"）
  2. 明天（1.5h）给 SKILL_ANATOMY.md 加"外置规则层"节
  3. 后天（0.5h）Upskill Trainer SPEC.md 登记 L1.5 模块（F9）
  4. 本周内（2h）手写 ikea-confluence-to-deck 的 rules/ 骨架（不写代码，只写 3 个规则 Markdown，验证"外置规则"在 IKEA 场景是否更好改）
漏洞 1（最关键）：videocut-skills 成功高度依赖火山引擎 ASR 字级时间戳——IKEA 场景的"关键依赖"是什么？→ Confluence 页面结构化质量（PRD 模板可，自由格式会议纪要不行）；Metabase 指标口径稳定性。
漏洞 2：自进化在多人协作下会 git merge conflict + 规则语义冲突。单人仓库的优雅模式搬到大组织会变重——需 CODEOWNERS。
漏洞 3：审核页阀门在 CI/CD 或远程 Copilot CLI 会话跑不起来——限定"本地 Agent 场景"。
依赖顺序（隐藏的坑）：外置规则层 → 审核页阀门 → 自进化闭环（后两者依赖前者），不能并行推进。

用 Pake (Tauri) 给 IKEA CDH 做 Electron 减负 PoC

✅ Verified · 56.6K⭐ 信号：@precisox / tw93 2026-06-20 关联：Apple Notes / AI Starter Kit / my-dotfiles
核心主张：用 tw93/Pake（Rust + Tauri）在1 天内把一个 IKEA 内部 Web 工具（Confluence 门户）重打包为 ~5MB 原生桌面应用，实测内存/启动/包体三项数据，作为 CDH"Electron 减负"的 Go/No-Go 决策依据——而非先去说服 IT 或写 RFC。

🎯 锁定痛点

CDH 工程师日常挂 3-5 个 Electron 应用（Slack 600-900MB / Teams 400-600MB / 内部工具），合计常驻 1.2-1.9GB——占 16GB Mac 的 8-12%。Docker + IDE + Electron 叠加 → swap → 风扇 → 续航缩水。内部 Web 工具"桌面化"成本陡：Electron 太重，PWA 失全局快捷键，原生重写杀鸡牛刀。Pake 是缺失的中间态。

📅 里程碑

  • M1（本周，1 天）：5 分钟 PoC + 数据采集。npx pake-cli 打包 Confluence，测包体/空载内存/冷启动。Go/No-Go：内存 < Chrome 标签 50% & 启动 < 2s & 包体 < 20MB
  • M2（Week 1-2）：内部 brown-bag + 1 位 oncall 工程师志愿者（标签页地狱最严重的人）试用 1 周
  • M3（Week 2-3）：扩展到 3 个工具（Confluence / AI Genie / Grafana dashboard）
  • M4（Month 2）：仅当 M1-M3 全绿，才找 IT 谈 Windows image 分发
  • M5（Q3）：Go（全团队推广）/ Narrow（仅 Mac）/ No-Go 决策

💰 ROI

保守年化（Mac 团队 30% 采纳）~¥254K（内存释放 → 减少卡顿 → 节省时间），99% 来自不可验证推断，仅作上限不作预期
定性品味落地（Apple Notes FileProvider 同公理）、AIE Code 议题素材、Starter Kit 自然延伸
✅ 本周立即行动：
  1. 今天（<2h）5 分钟 PoC：npx pake-cli https://confluence.build.ingka.ikea.com --name "IKEA Confluence"，采集包体/内存/启动 3 个数字。无论好坏都有价值
  2. 周三前（1h）发 1 分钟问卷：团队 Electron 负债 + 浏览器标签地狱基线
  3. 周五前（10min）私聊 1 位 oncall 工程师锁定 M2 志愿者
挑战 1（最致命）：Tauri/Pake 在 IKEA Windows image 几乎装不进去——Microsoft 已取消 EV 证书绕过 SmartScreen 的特权（Tauri 官方文档过时），MSI 缺 package identity 无法 Intune 管理。M4 可能耗时 2-6 个月。这就是为什么 M1-M3 全设计为"仅 Mac、不依赖 IT"——Windows 是天花板但不作 PoC 前提。
挑战 2：WebView 本身不等于"零 Chromium 内存"——复杂 Confluence 页在 WKWebView 仍可能 200-300MB。M1 唯一目的就是证伪/证实。
挑战 3：Apple Notes FileProvider 教训——原生扩展开发成本高，PoC 容易卡 UI 层。严格限定 Pake 为"现成工具打包"，绝不自己写 Tauri/Rust 扩展。
挑战 4：PWA 会不会就够了？→ M1 应同时测 PWA 作对照组。若 PWA ≈ Pake，优先推 PWA（零 IT 审计）。

浏览器即 OS：把四工具栈升级为 Agent 用户态抽象层

✅ Verified · 趋势确认 信号：@Cander_zhu 2026-06-22（How modern browsers work 读后感） 关联：Browser Automation / Agentic Engineering
核心主张：浏览器是 OS；Kyle 的四个工具（bb-browser + opencli + chrome-devtools + /browse skill）已经是这个 OS 的用户态，只是还没有人把它们命名为"用户态"。提案的本质不是"第 5 个工具"，而是把 /web-browsing SKILL.md 里 Agent 每次重新解释的决策文档，变成编译期固化的 dispatcher 函数。

🗺️ 已验证的工具栈 → OS 原语映射

  • chrome-devtools（Rust 直连 CDP）= 内核 syscall 接口
  • bb-browser（198 适配器）= libc + 文件系统
  • internal/sharepoint adapter = FUSE / 凭证挂载点
  • opencli explore/generate = 动态加载器（运行时合成新 syscall）
  • /browse skill（headless Chromium）= 独立沙盒 VM

🆕 三个未被占领的 OS 高地

  • 机会 A（Service Worker = Agent 守护进程）：离线任务队列，提交后断开、完成取回。但受同源约束，可行性 < 机会 B
  • 机会 B（File System Access API = Agent 家目录）：Web 文件当本地文件写，跨会话持久。建议优先验证（纯客户端，无需站点配合）
  • 机会 C（Broadcast Channel + Web Locks = 跨 tab IPC + 互斥锁）：多 Agent 协作基础，优先级低

📅 路线图（每阶段有继续/停止判定门）

  • Phase 1（本周-下周，零生产改动）：198 适配器 syscall 分级（L0 file-like / L1 ipc-like / L2 mount-like / L3 syscall-like）+ IPv6 CDP 绕过脚本化 + OS 能力探针。判定门：L0 占比 > 75% 且 FS Access API 可用 → 继续
  • Phase 2（1-2 周）：薄 dispatcher 原型（~50-100 行，固化 Decision Matrix）+ FS Access API 给 SharePoint 适配器加"下载到家目录"
  • Phase 3（2-4 周）：给 1-2 个高频内部适配器增加 IndexedDB + 家目录支持

💰 ROI

Agent 决策 token当前 ~3-5K（读 SKILL.md）→ 目标 < 1K（dispatcher 固化）
文件下载手动步骤SharePoint 场景 3 步 → 1 步（FS Access API 自动写家目录）
长任务可断开场景0 → ≥1（证明 SW/IndexedDB 异步模型）
✅ 本周立即行动：
  1. 2-4h 对 198 适配器做 OS syscall 分级：导出清单，按 readOnly/capabilities 字段分 L0/L1/L2/L3，产出分级表。用数据回答"抽象层是否值得做"
  2. 把 IPv6 CDP 绕过从"故障排查段"升级为标准启动脚本（SKILL.md 第 142-173 行已有方案，埋没了）
  3. 跑 OS 能力探针：bb-browser eval 探测 showDirectoryPicker/serviceWorker/BroadcastChannel/Web Locks 可用性
挑战 1（最强）：已经有 4 个工具了，再加抽象层是不是过度工程？→ 抽象层不是第 5 个工具，是把已有的决策文档变成代码（~50 行）。判定标准：若 dispatcher 实际只用 2-3 条决策路径（90% 场景"有 adapter 用 adapter"），就不要做 dispatcher，保持文档形式。
挑战 2：Chrome 自己在做 Agent 适配（WebDriver BiDi / Agent Mode），12 个月后还有价值吗？→ 内核演进不消灭用户态库（Linux glibc 至今健在）。但通用平台适配器可能被 Chrome 吃掉——企业内部适配器（Admin Portal/MIP）才是长期护城河。战略含义：精力从"维护 198 公开适配器"转向"深耕企业内部"。
挑战 3：SW/FS Access API 是内核特性，Agent 在用户态能注入吗？→ FS Access API 可以（纯客户端，任意页面 eval 即可）；SW 受同源约束，对内部站点降级为"不可行"。优先验证机会 B。
