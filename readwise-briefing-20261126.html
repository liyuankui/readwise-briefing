腾讯云开放元宝搜索：面向大模型和 Agent 的搜索引擎✅ 全文已读

11-25 · 知乎专栏（腾讯云 10-20 官宣的第三方梳理）

腾讯云（非元宝 App）把内部跑了一年的搜索能力对外开放：过去供货 50+ 核心业务、日均调用数亿次。接入方式 Skill / MCP / API 三种（网传「插件」说法为误传，两个独立信源逐字一致）。新用户每月 2000 次免费调用。能力数字：全网覆盖率 96%、千亿级向量索引、94% 召回率下底层检索 8ms、排序推理 149ms→30ms（Gist Token 压缩长文喂给排序模型）、157 个签约权威信源（申万宏源/携程/飞常准等，A/H/美/日/韩股财报覆盖 99%+，政策/行情分钟级更新）。真实案例：ima 信源召回 +10%、腾讯视频模糊找片覆盖 +20%。

① 直接竞品是个人工具链在用的搜索 API（Tavily/博查）——2000 次/月免费 + 157 个签约信源意味着国内场景的调研/时效搜索多了一个低成本选项；签约信源（财报/金融/法律）是网页抓取型 API 结构性拿不到的，这与 K12 AI 教育项目和公众号选题调研都相关。② 「Skill / MCP / API 三通道」是把搜索与自家 Agent 生态捆绑卖的样本——开放的是搜索，捆绑的是生态，对理解平台型 Agent 能力分发的打法有参考价值。③ MCP server 端点官方尚未放出，网上已现假配置教程——接入须以控制台为准，勿抄搜索结果。原文

How to Build an AI Code Assistant⚠️ Partial · Part 1 免费

11-25 · systemdesign.one

AI 编码助手实为三个约束不同的子系统：Autocomplete（~300ms 预算，拼延迟）、Chat（秒级，拼代码库检索）、Agent（分钟级，拼信任/审批）。要点：FIM（Fill-in-the-Middle）结构让补全贴合光标前后；延迟预算是零和的（上下文组装 ~80ms + TTFT 主导剩余，编辑器必须克制选上下文）；模型选型先看能否在硬预算内完成 prefill 再看准确率（1-3B 适合本机补全，7B 更准但易超时，Cody 换小模型后延迟降、接受率反升）；评估用留存而非接受率——接受率因「短而显然的建议」虚高，GitHub 用 retained characters、Cody 用编辑距离追踪被接受后是否存活。

① 与 eval 方法论主线（三大鸿沟/过度思考/OTel）四连互证——这篇补上了「指标本身会说谎」这一层：接受率虚高的机理（短建议 bias）与 judge 校准是同一问题的两面，可直接进讲师团 eval 课程的「度量陷阱」小节。② 300ms 零和预算的架构哲学（组件克制地共享窄窗）与调度系统「慢决策=坏决策」同构，两天两源指向同一设计原则。③ Part 2-6（repo 探索/路由/沙箱/评估）在付费墙后，Part 1 的补全子系统已完整可采信。原文
