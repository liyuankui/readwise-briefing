2锁定的具体痛点

OpenMAIC 当前走 Cloudflare Workers + AI Gateway (BYOK) 的云端模型路径。真实痛点：

  • 网络/准入：教室弱网或离线即瘫痪；BYOK 要每个环境配 key。
  • K12 隐私：未成年人对话数据上云有合规与伦理顾虑。
  • 成本可持续：「纯免费部署」是项目旗帜，长期 token 费与之相悖。
  • 延迟：多 agent 教室对话对 p95 延迟敏感。

P3 · 采用 Docker Sandboxes 作为 Life OS 的隔离底座
信号：HN 2026-08-11 #3 · ✅ Verified · 关联意图：Life OS（Software Factory + Trust & Eval）
核心主张｜用 Docker Sandboxes（microVM，独立内核）做 Life OS 的物理隔离底座——把 Software Factory 从「人盯模式」推进到「无人值守 YOLO」，让 Trust & Eval 第一次有真实的 blast-radius 边界。没有物理隔离，自主 = 自毁。

2锁定的具体痛点

当前 Kyle 的 agents（Claude Code / Gemini CLI / Codex 等）直接跑在主机上。三个互相强化的痛点：

#痛点现状后果
P1主机直跑 = blast radius = 整台机器 + 全部知识库一个 rm -rf / 恶意 postinstall / prompt injection 的 curl|bash 就能抹掉多年积累
P2YOLO 风险高 → 不敢真正放权Software Factory 永远停在「人盯 executor」——Kyle 仍是 executor，非 system designer
P3Trust & Eval 缺物理底座eval 再准也挡不住 agent 物理搞坏主机；隔离是 eval 的前置，非并列项

为什么 devcontainer 不够：devcontainer 共享主机内核，挡不住容器逃逸 CVE，且 nested Docker (DinD) 是雷区。Software Factory 里 agent 要自己起测试容器——Docker Sandbox 每实例自带独立 Docker daemon，nested 容器是原生能力。结构性差异，非配置能补。

3实施里程碑

里程碑周期Done = ?
M1 · sbx 上路0.5 天装好 sbx、跑通 hello-world，microVM 内 uname -a ≠ 主机内核；销毁后主机 git status clean
M2 · 第一个 sandbox PR≤1 周选个人 repo 一个小 issue，agent 在 sbx 内 clone→code→test→commit→push→开 PR，全程主机零改动
M3 · egress 加固1-2 周sandbox 默认无网，allowlist 放行（pypi/npm/github/registry），其余 DROP；故意 curl 非 allowlist 域名 → 被拒
M4 · Factory 编排集成2-3 周每个任务起 disposable sandbox，结束即销毁；intent→Factory→sandbox→自动 PR
M5 · Eval 沙箱化持续eval/canary 任务跑 sandbox，N≥10 连续任务主机 clean

关键决策：M3 不可后移。microVM 不挡外发网络（案例：某工具上传 5.1GB 而实际只需 192KB）。M2 之后立即加固 egress，否则信任底座是漏的。

4成功标准

  • 自主产出：agent 在 sandbox 内独立完成并被 merge 的 PR ≥1（30 天内累计 ≥5）。
  • 主机完整性：sandbox 运行期间主机 git status 100% clean。
  • 资源纪律：单 sandbox 内存峰值 ≤8GB；与本地 ollama 共存不 OOM。
  • 冷启动：起一个 sandbox <5s。

5ROI

杠杆说明
解锁放权没隔离 → Kyle 永远是 executor；有隔离 → 升级为 system designer。身份跃迁，非工具升级。
Trust & Eval 地基eval 结论在不污染主机的环境里才可信、可复现、可回滚。
沉没成本已付docker 29.4 已装；sbx 是 standalone CLI，门槛一条 brew install。
正交于模型选型云模型还是本地都不影响隔离层。模型会换，隔离底座不变——寿命最长的投资。

6风险与缓解

  • microVM 不挡外发网络（🔴 High）：默认禁网 + egress allowlist + 可选 TLS proxy 审计；把「任意外发」压成「allowlist 内外发」，攻击面缩 2 个数量级。
  • 24GB RAM 争抢（🟡 Med）：sandbox 硬限 ≤8GB；Factory 任务与本地模型推理分时调度（不并发）；默认云模型，本地模型按需起停。
  • sbx 是新产品（🟡 Med）：先在个人非内网仓库跑 M2；每里程碑写 postmortem；保留 devcontainer fallback。
  • 公司内网合规（🟡 Med）：公司内网仓库的 sandbox 任务仅本地跑、不触公网；egress allowlist 排除一切非公司 registry；先与安全方确认 microVM 是否满足内网数据处理要求。

7立即行动（本周 3 件事）

  1. 装 sbx 跑通官方 demo：brew install docker/tap/sbx && sbx login；sandbox 内 uname -a ≠ 主机内核。
  2. sandbox 内跑通一个真实小 PR（readwise-briefing / notebooks-dashboard 低风险 issue）：clone→code→test→push→开 PR，主机零改动。
  3. 写 egress allowlist 草稿 v0：列允许域名 + 默认 DROP，remarker open review。
诚实挑战｜Q1 真比 devcontainer+权限收紧好吗？ 若仍人盯，devcontainer + --cap-drop ALL --network none 已够，microVM 是 over-engineering。若目标是无人值守 YOLO（Life OS 明确意图），microVM 必要：防御深度 + nested Docker 原生 + 可抛弃性。Q2 网络缺口要额外 egress firewall 吗？ 必须，非可选。Sandbox 解决「炸主机」不解决「偷数据」，两者正交。Q3 会不会 over-invest 早期产品？ M1+M2 <1.5 天，放弃也是廉价学费；真正风险是「不动手就永远停在 executor」。

P4 · 将 Claude Code Auto-Mode 纳入 Engineering Baseline
信号：HN 2026-08-11 #9 · ✅ Verified · ⚠️ 17% 漏报 · 关联意图：Engineering Baseline / WellDone / Life OS
核心主张｜以「分类器自动放行 + 静态 denylist 前置 + PR/测试/blast-radius 补偿控制」三明治结构，把 auto-mode 立为自治编码标准——危险命令拦截率从人审 13.6% 拉到 >95%，同时消除每条命令手动审批的注意力税。

2锁定的具体痛点

痛点现状auto-mode 后
注意力税每条 Bash/Edit 手动 y/n，团队年累可观数百小时审批工时 + 焦点切换损耗safe 调用零摩擦放行

杠杆点：13.6% vs 89% 不是「机器 vs 谨慎的人」，而是「机器 vs 走神的人」。手动审批的「安全感」是 Status Quo Bias。但 89% 仍漏 11%、独立压测 17% FN——补偿控制是刚需，不是可选。

4成功标准

  • 1 个真实 PR：需求到合并，agent 全程自主，人仅 review ← 直击「agent 完成完整 PR」。
  • 0 主机事故：审计日志 + canary 文件双重验证（无逃逸、无密钥外泄、无主机 FS 改写）。
  • RAM 峰值 <20GB：守 24GB 约束，留 ≥4GB 给系统 ← 诚实量化。
  • Guardrail 红队：50 危险命令执行数 =0；50 安全命令误拦 ≤5。
  • 1 个高频任务全自动化：deps bump / doc sync / skill lint，cron 触发，rig 出 PR ← 直击「one high-freq task fully auto」。

6风险与缓解（直面 24GB 三难）

三难账：Glimmer 30B 4-bit 峰值 ~22GB + microVM ≥2-4GB + 本地分类器 7B 4-bit ~5GB
        + macOS ~6-8GB ≈ 30GB+，爆 24GB。三者【不能同时本地】。
  • RAM 爆炸：(1) 分类器上云（最 stateless，走 API，本地零占用）——必须的切；(2) Brain 默认跑小模（Qwen3-14B ~8GB），仅硬任务按需热加载 Glimmer 4-bit，用完卸载；(3) microVM 按需启停。目标常驻 <14GB，峰值 <20GB。
  • 网络 exfiltration：独立 netns + egress allowlist 代理；密钥永不挂载进沙箱（~/.ssh/~/.aws/private 一律不映射）；macOS pf 限虚拟网卡出站。
  • 17% 误漏：纵深防御——沙箱兜底（漏过者困 VM 内）+ 每条 Bash 审计入日志 + 每周红队回归 + fail-closed（分类器宕机即全挡，保留限时人工 override）。
  • Glimmer 仅微胜 Qwen3.6：勿过度投资；M1 基准若 Qwen3-14B 性价比更优，弃 Glimmer 主力位。
  • 公司合规：内部代码能否上个人笔记本本地跑？动手前用安全审计 skill 过审；公司仓库暂不接入，先在个人 repo 验证。

7立即行动（本周 3 件）

  1. 装 Docker Sandboxes + blast-radius 冒烟（2h）：VM 内 rm -rf /、cat /etc/passwd、试读 ~/.ssh，确认主机无伤、无泄。先验 Body 可信。
  2. 拉 Muse Glimmer 4-bit + 跑 1 个 SWE-Bench-lite 任务（1 晚）：实测 RAM 峰值与 p50 延迟。数据出才谈取舍，不假设。
  3. 起草策略配置 + eval 评分表（半天）：allowlist（读/测试/commit）+ denylist（密钥、force push、rm 主机路径）；写「什么是好 PR」rubric（可编译、测试过、diff 可读、意图相符）。
诚实挑战｜Q1 复杂度是否违背 Life OS「简化」初衷？ 是真实风险，易陷「调 rig 代替用 rig」。解药：买基础设施（Sandboxes/Ollama/Claude Code 皆采用非自造），只自建三样——编排 glue、eval 评分、policy。接口约束为一条命令（agent: ship this）。时间盒：搭建 ≤2 周；之后度量「经 rig 合并的 PR 数」非「组件数」。Q2 本地 vs 云端 ROI 拐点？ 本地赢在私密/高频低成本/低延迟/主权学习；云端赢在能力上限。拐点：routine 80%（个人 repo/chore/lint）走本地，hard 20%（关键路径/frontier 推理）走云端。别追求 100% 本地——那是洁癖，非 ROI。 Q3 EM 时间最稀缺，先买还是先建？ 大部分买，小部分建。买：Claude Code 订阅、Sandboxes、Ollama。建：glue + eval harness + policy——这才是 Life OS 真正资产。Kyle 稀缺时间应花在 eval 评分表与 policy，而非 microVM 调优。
