Proposal 1BrowserSkill 试点：把登录态网页操作交给 Agent，个人设备先行

日期 2026-09-17 · 状态 Draft v2 · 决策窗口 4 周 · 投入上限 ~12 h

事实快照（三级证据分级）

腾讯开源 BrowserSkill（CLI + 浏览器扩展）：让任何能跑 shell 的 Agent 直接操作用户真实、已登录的浏览器；任务跑在独立 Agent Window，标签页显式借用/归还，内置 human-in-loop。与 browser-use（驱动自带干净 Chromium）的差异 = 登录态复用 + 不打断用户 + human-in-loop + 远程回连（0.3.0：云端 Agent 经一次性配对与可吊销设备凭证，走 TLS WSS 回连本地浏览器——稀缺能力）。

证据等级内容
已实证MIT 开源（TS+Rust）；上线 3 个月 3002 stars，昨日仍活跃提交；CLI 30 秒装好（实测 0.2.1），命令面 Playwright 级；install.sh 未经确认改写 shell 配置（已清理）
文档级（待实证）四层链路 Agent→CLI→daemon→扩展→Agent Window，Agent 永不直碰浏览器；会话内串行、跨会话并行、stop 归还借用标签；四条权限收敛（写操作沙箱、权限权威只在浏览器侧、文件传输三方分权、凭证零提取 + 30 天审计日志）；SKILL.md 防御性纪律（导航后必须重新 observe、禁点旧截图、borrow 被拒即停、Canvas 用 2 分钟过期 capture_id）
完全未验真实配对体验、Agent Window 体验、扩展出网行为、远程模式

1 · 核心主张

用 4 周、约 12 小时，在个人设备的专用浏览器 profile 上完成安全实证与双 harness 对比评测——含对官方「四条权限收敛」声明的逐条验证——把「登录态网页自动化」从直觉变成可测量决策：与 browser-use 按信任分层并存，或放弃；远程模式一律延后至 Phase 2。

不预设 BrowserSkill 好用，只预设「这个问题值得 12 小时验证」。

2 · 锁定痛点

#场景现状断点对应能力
P1登录态数据导出：个人站点后台、电商订单与发票、报表下载，每次手动点 5–10 层菜单干净 Chromium 无 cookie，卡死在登录（密码+2FA+验证码）；凭据注入又污染既有凭据管理复用真实登录态
P2RPA 型长任务与日常浏览互斥：自动化一开，浏览器被独占或藏进 headless任务不可见、不可接手，用户被迫干等独立 Agent Window，标签显式借还
P3遇 human-only 环节即断：验证码、二次登录、弹窗；定时/云端任务更是完全够不着本地登录态任务失败状态即丢；服务器上的 Agent 无法使用本地浏览器human-in-loop；远程回连（Phase 2 验证）

3 · 实施里程碑

#内容交付物估算
M1个人设备新建专用浏览器 profile，装扩展，完成配对，跑通 1 个真实登录态任务（打开→定位→导出/截图）配对验证记录 + 安装副作用清单第 1 周 · 1.5 h
M2安全模型逐条实证：①试以 CLI 覆盖自动化开关（应失败）②试提取 cookie（应失败）③borrow 被拒后观察是否停手不绕过④核验 30 天审计日志；同步审计扩展权限与 daemon 出网行为；立守则、封装 skill四条权限收敛验证清单 + 守则 v1 + 封装 skill第 1–2 周 · 3 h
M3双 harness 对比评测：8 个真实任务（4 登录态 + 4 公开）× browser-use/BrowserSkill × 各 3 次评测报告（可公开发布）第 2–3 周 · 4 h
M4选 1 个高频登录态流程（如数据导出）做成每周本地流水（远程模式不开）1 条常态流水 + 前后时间账第 3–4 周 · 2 h
M5复盘决策：并存 / 收敛 / 放弃 + 是否开启 Phase 2（远程模式）；公开文章决策备忘 + 评测文发布第 4 周 · 1 h

4 · 成功标准（全部可测量）

维度指标阈值
可用M1 配对与首任务一次跑通，< 30 min
安全实证四条权限收敛（开关覆盖 / cookie 提取 / borrow 门控 / 审计日志）逐条复现官方声明；任一证伪 → 直接进 M5 重估信任基础
效果登录态任务成功率（4 任务 × 3 次）BrowserSkill ≥ 75%；browser-use 不注入凭据基线预期 < 25%（对照组）
干预平均人工介入次数≤ 1 次/任务
安全运行越权事件（白名单外访问、凭据提取尝试）0 次，且拦截有日志可查
价值连续 2 周时间账每周净省 ≥ 30 min
产出公开评测文 + 决策备忘1 + 1，第 4 周末发布

任一不达标即触发 M5「放弃」分支——失败也被定义清楚，此为本提案的可证伪性。

5 · ROI / 影响估算

项估算
投入~12 h / 4 周；工具免费（MIT）
直接回收登录态操作每周省 45–90 min（以 M4 时间账为准），2–3 个月回本
方法论资产① harness 评测新增「登录态任务」维度，并入现有 model × harness 评测框架；② 四条权限收敛验证清单可复用为任何「Agent × 浏览器」工具的安全验收模板；③ 沉淀「新 Agent 工具引入四步流程」（审计→隔离试点→对比评测→决策），可复制到任何后续工具
影响放大《Agent 使用真实浏览器安全守则》公开化——该项目 3 个月 3000 stars，社区正缺这份边界文档

最大收益不是省时间，是把「敢不敢把登录态交给 Agent」第一次给出工程化答案。

6 · 风险与缓解

#风险缓解
R1登录态 = 数字身份。官方四条权限收敛设计优于同类，但两点残余：① Agent Window 标签继承 profile 登录态，窗口内已登录操作不经 borrow 门控，prompt injection 仍可下单/删数据；② 以上均为设计声明，3 个月项目、无第三方审计M2 逐条实证；专用 profile 只登低敏感账号；站点白名单 + 高危操作黑名单；human-in-loop 强制；审计日志留存。防线排序：隔离 > 架构实证 > 白名单 > 审计 > 提示词纪律
R2公司设备 vs 个人设备。公司设备受终端监控与合规约束，真实浏览器含企业 SSO 登录态，接第三方开源工具可能违规或触发告警；远程模式更是安全团队重点监视线行为硬边界：公司设备不装、不连、不试；远程模式在公司上下文绝对禁用；仅个人设备 + 个人账号 profile；企业场景须先过正式安全评估，不在本提案范围
R3与 browser-use 的关系：并存，不替代。两者属不同信任层公开任务 → browser-use（干净、可重置，默认工具）；登录态任务 → BrowserSkill（白名单启用）。仅当 M3 公开任务组中 BrowserSkill 不劣且安全达标才议收敛——默认不收敛
R4远程模式：稀缺能力 = 稀缺攻击面。常驻 WSS 隧道直入浏览器；一次性 pairing link 可被钓鱼仿冒；30 天审计日志自产自销，无外部监督Phase 1 一律不开；Phase 2 触发条件 = M1–M4 全绿 + 四条收敛实证通过；届时仅连自有服务器、凭证短周期续期 + 吊销演练 + 出网白名单
R5供应链：install.sh 实测擅改 shell 配置；预编译二进制与源码一致性未验锁定具体版本；安装前 diff 审查脚本；校验 release 哈希或源码构建；M2 封装层隔离直调
R6项目仅 3 个月、0.2→0.3 间已弃用参数（--unattended），API 处于破坏性演化期经封装 skill 调用，升级只改一处；每次升级前 diff changelog；连续 1 个月无更新即降为「观察」
R7自动化已登录账号违反站点 ToS / 触发风控封号白名单排除金融与高价值账号；低频执行；异常即停并移出白名单

7 · 立即行动（本周）

  1. 配对首跑（~1.5 h）：个人设备，新建浏览器 profile → 装扩展 → 配对 → 跑通 1 个登录态任务，全程截图留证。
  2. 安全实证速验（~1 h）：先验两条最关键收敛——CLI 覆盖自动化开关应失败、cookie 提取应失败；读扩展 manifest 权限与 daemon 出网域名；写《Agent 浏览器使用守则》v0（10 行以内）。
  3. 痛点定量（~0.5 h）：记一周登录态网页操作时间账，圈定 M3 的 8 个评测任务——先证明痛点值 12 小时，再花 12 小时。

8 · 诚实挑战 红旗自审

  1. 痛点强度未定量，可能自我说服。「高频登录态操作」目前只是感觉；若时间账 < 30 min/周，ROI 崩塌，提案退化为技术尝鲜。故行动 3 前置，M1 之后随时可撤。
  2. 三类声明均未实证：安全声明（四条收敛）、体验声明（不打断用户、借还流畅）、能力声明（远程回连）目前全部来自文档与推文。M1/M2 只验前两类，远程留 Phase 2——验前一律不得外推，包括本提案自己引用的部分。
  3. 沙箱有残余缺口，安全与卖点结构性成反比。Agent Window 标签继承 profile cookie，窗口内操作不经 borrow 门控；官方把 borrow 决定权推回给人，本质是承认信任问题无技术解。硬闸只剩「专用 profile + 站点白名单」，而闸越紧场景越少——最安全时可能只剩「导出报表」一个用例。
  4. 远程模式双刃。对企业它同时是稀缺能力与标准否决项：安全评审大概率先问「隧道、钓鱼、日志可信度」三连。个人 Phase 1 不开是对的，但意味着 P3 后半段（云端定时任务）在本提案中并未被验证——宣称解决的痛点只验了一半。
  5. 评测设计易作弊。8 个任务自己挑、样本小，且登录态组对 browser-use 胜之不武（对手本无登录态）。结论只能主张「登录态任务选它」；替代与否只看公开任务组——混淆两者，评测就成了广告。
  6. 养护成本与 API 易变。0.3.0 已弃用参数证明接口仍在破坏性演化；daemon + 扩展 + CLI 三件套进入个人工具链，3 个月项目无长期承诺。若半年弃坑，残值只剩守则、评测方法与封装层——故交付物一律设计成「工具死了也留得下」的形态。
