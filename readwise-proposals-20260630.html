PROPOSAL 03 · ⚠️ 数字已修正

FastContext 探索路由：小模型当仓库探索者

接 LLM 网关调研 ⚠️ 60% 含义修正 12 周
在 IKEA LLM 网关加一条"探索路由"：把 Agent 工作流中"找相关代码"这步路由给自托管 4B 小模型，只让贵模型做真正代码生成——不改 Agent 主框架，降低单任务主模型 token。
⚠️ 必读：先纠正一个会被追问翻车的数字。原推"Agent 60% token 花在搜索代码"是误读。论文原文是"集成 FastContext 后主 Agent token 降低（最多）60%"——60% 是节省幅度，不是搜索占比。对外汇报若用错表述，会被任何读过论文的人当场抓包。全程用"降低 60%"表述。

🎯 锁定痛点（三层可量化）

  1. 大仓 bug fix 探索吃前沿模型 token：IKEA Java/Golang 仓体量大，Agent 反复 grep/读文件按 GPT-4 级单价计费，而这些调用本质是检索——用 GPT-4 做 grep 是 token 用错了地方。
  2. 没有"单任务成本"度量：网关调研阶段尚无按任务聚合的 token/成本埋点，省没省钱全靠感觉。这是比上不上 FastContext 更优先补的缺口。
  3. 探索与生成耦合在同一模型，无法对探索单独换便宜模型或缓存。

PROPOSAL 05 · 抄你已验证的范式

给 100+ Skills 装一张能力路由表 (capability-router)

接 my-skill-manager 生态 ✅ 6h 可见雏形 6 天
与其让 Agent 在 100+ SKILL.md 里做关键词模糊匹配猜技能，不如给它一张声明式"任务意图→技能"路由表，让 Agent 自决策走哪条路——就像 agent-reach 已在 15 平台做到的，只是这次路由"能力"而非"平台"。

🎯 锁定痛点（实测证据）

  • 靠子串匹配选不准：skill-finder 用 query in name/description 子串包含，零语义零意图理解。
  • 推荐是硬编码 if-else：Node→react-component-dev、Go→go-engineering 是写死的，新增技能必须改代码——与"声明式"相反。
  • 同域多技能必错选：5 个安全技能（ikea-security/credential-manager/git-crypt-manager/cred-vault/cdh-client-skill-safer），Agent 搜"security"只命中部分且无法判断该用哪个。
  • 3 个技能 description 残缺（cloudflare 空、cred-vault/humanizer-zh 占位），在关键词搜索里等于隐形。

一句话：你有数据层(skill-manager 31k JSON)和检索层(skill-finder)，缺决策层(routing table)。

🗺️ 里程碑

M1 分类法100+ 技能归 8-12 capability domain（dev/doc/test/security/ikea-ops/content/knowledge/infra...）0.5 天
M2 主路由表照搬 agent-reach SKILL.md 结构：standing rules + routing table（单一事实源）1 天
M3 references每域一个文件，存"辨析表"（任务→用谁/不用谁），禁止抄 description2 天
M4 解耦skill-finder 保留作表外 fallback；删 _get_recommendations() 硬编码 if-else1 天
M5 补全+README修残缺 description；写"何时查表/何时 fallback/如何加路由"运维手册1 天

🔥 诚实挑战（单点成败）："会不会又是一个没人维护的中间层？" 真正风险。唯一缓解：把它钩进 my-skill-creator——新建技能 checklist 第一条加"已更新 routing.md"。如果连这条都不做，路由表 3 个月后必漂移成废纸。这是成败单点。
