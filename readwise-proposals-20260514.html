GBrain → Life OS Memory：给 IRA 补上"编译"步骤
Life OS · Memory
GBrain 最值得借鉴的不是知识图谱，而是 Compiled Truth + Timeline 双层结构——一个实体一页，顶部可重写综合结论，底部不可变证据链。这恰好补了 IRA 的关键缺口：ingest-agent 只做追加，没有"编译"步骤。
🎯 锁定痛点

当前 context/ 目录只有"追加"没有"综合"——信息越多越难找，Agent 每次都从零搜索。缺少一个让知识自动复利的"编译器"。

📍 里程碑
M0创建 context/entities/ 目录 + 写 SPEC 授权 compile-agent M1手动对 3 个高频实体（Remarker / Baozun / Skill Hub）编写 Compiled Truth + Timeline M2实现 compile-agent prompt：读 journal + context → 自动生成/更新 entity page M3regex 关系提取（zero LLM）：实体间自动建 backlink
✅ 成功标准
  • Agent 回答"Remarker 当前状态"时，命中 compiled truth 而非搜索 20+ journal
  • 新 session 冷启动时间减少 50%（从读 context/ 到获得项目全貌）
⚡ 本周立即行动
  • 创建 context/entities/ 目录 + README
  • 手写 Remarker entity page（Compiled Truth + Timeline 格式）
  • 在 SPEC.md 中授权 compile-agent 可重写 entity 顶部
🔴 诚实挑战："编译"什么时候触发？手动太累，自动可能产生幻觉。GBrain 用 regex 做关系提取（确定性），但"综合结论"仍需 LLM——LLM 编译的准确性谁来验证？需要设计 human-in-the-loop 的编译审核机制。
2
Agent Harness 自动优化器：先造尺子，再造机器
Project Harness
Prose harness（VISION/SPEC/OPS）的自动优化可行，但前提是先解决"评分信号稀疏"问题——你得先有 benchmark 才能谈优化。Meta-Harness 已证明 +33% 提升，但它依赖完整执行 trace（~10M tokens/轮）。
🎯 锁定痛点

15+ 项目的 harness 维护全靠手动反馈循环。skill-evolver 依赖人发现问题→诊断→修复，没有自动化的"质量仪表盘"。

📍 里程碑
M0研究 Meta-Harness (Stanford IRIS Lab) 架构，判断适配性 M1构造 1 个 skill benchmark（定义任务 + 预期输出 + 评分规则）— Go/No-Go 决策点 M2对 benchmark 跑 A/B 测试：当前 harness vs 优化后 harness M3自动化循环：优化器生成提案 → benchmark 评分 → 保留/丢弃
✅ 成功标准
  • 至少 1 个 skill 的 benchmark 通过率提升 >15%
  • Harness 迭代周期从"天"缩短到"小时"
⚡ 本周立即行动
  • 克隆 Meta-Harness 仓库，阅读架构文档
  • 选定 1 个 skill（如 journal）设计 benchmark 任务集
  • 定义"好 harness"的 3 个可量化维度
🔴 诚实挑战：Prose 优化的评分信号天然稀疏——"VISION.md 写得好"怎么量化？代码有测试通过率，prose 没有。可能需要"代理指标"：Agent 在该 harness 下完成任务的成功率、hallucination 率、人工修正次数。这套评价体系本身的构建成本可能 > 直接手动优化。
3
CI/CD 缓存投毒防御：GHES 的差异化风险评估
IKEA Security · Skill Hub
GHES 封闭性降低外部攻击概率，但 self-hosted runner 持久化 + 内部人 PR 权限 + 无 skill 完整性校验构成差异化风险。npx skills add 的风险不在传输层，在源头——skill 仓库 CI 若被投毒，发布物本身就是恶意的。
🎯 锁定痛点

上周 PII 事件耗时 3+ 小时，属于被动响应。没有前置防护机制（pre-commit hook / CI 缓存审计 / skill 签名验证）。

📍 里程碑
M0 本周30 分钟审计：扫描所有 GHES workflow，检查缓存使用和 runner 共享情况 M1实施 Quick Win：PR workflow 隔离（read-only token）+ 缓存 scope 限制 M2Skill 完整性校验：npx skills add 增加 checksum 验证 M3安全 runbook：CI/CD 事件响应 SOP + 定期审计机制
✅ 成功标准
  • 所有 PR workflow 使用 read-only token（零 cache 写权限）
  • skill 安装链有 checksum 校验，篡改可检测
  • 安全事件响应从"小时级被动"降为"分钟级主动"
⚡ 本周立即行动
  • 扫描 china-digital-hub/skills 的 CI workflow 缓存配置
  • 检查 GHES self-hosted runner 是否跨 repo 共享
  • 将 TanStack 攻击分析分享给团队（安全意识提升）
🔴 诚实挑战：GHES 的真实攻击面取决于 IKEA IT Infra 的 runner 配置，你可能没有 admin 权限查看。且 skill 生态还小（51 个），过度安全投入的 ROI 需要平衡。建议 M0 审计后根据发现再决定是否推进 M1-M3。
4
AI Upskill 双轨制：工具体感 + 元技能判断力
AI Upskill Trainer
不是从"教工具"转向"教判断力"，而是双轨并行——L0-L1 仍教具体工具建立体感，L2+ 重心转向评估、选择、迁移的元技能。课程架构设计为"框架+插槽"，工具可换但方法论不变。
🎯 锁定痛点

AI 工具迭代速度 > 课程更新速度。如果课程绑死具体工具（如"Copilot 使用指南"），3 个月就过时。用户真正缺的不是"哪个按钮在哪"，而是"面对 10 个工具怎么选"。

📍 里程碑
M0设计 L0 对比体验课：同一任务用 3 个工具完成，让学员感受差异 M1起草"AI 工具评估模板" v0.1（维度：场景匹配度 / 数据安全 / 学习曲线 / 成本） M2L2 课程改版：从"工具教学"改为"评估框架 + 工具实操"双模块 M3Pilot 验证：2 个非技术用户用评估模板自主选工具
✅ 成功标准
  • 学员能独立评估一个新 AI 工具（用模板，<15 分钟）
  • 课程更新不因工具迭代而重写（框架不变，插槽换工具）
⚡ 本周立即行动
  • 设计 L0 对比体验课的任务和 3 个候选工具
  • 起草 AI 工具评估模板 v0.1
  • 找 2 个 Pilot 用户验证"评估模板"是否好用
🔴 诚实挑战："教判断力"比"教操作"难 10 倍——操作可以演示，判断力需要体验积累。L0-L1 的"工具体感"阶段不能跳过，否则"评估框架"变成纸上谈兵。风险是双轨制增加课程复杂度，P0 缺口的讲师更难招。
5
Remarker 定位：护城河在协议层，不在功能层
Remarker
Remarker 的护城河不在功能（可抄），在三层递进：①协议层——颜色语义+行号定位的结构化反馈格式；②工作流层——嵌入 AGENTS.md 的标准操作，Agent 行为绑定；③习惯层——组织采纳后的切换成本。
🎯 锁定痛点

6+ 新 Markdown 工具密集出现，纯"查看/编辑"是 table stakes。Remarker 如果只是"又一个 Markdown 查看器"，没有存活空间。唯一差异化：AI 审阅循环是现有工具未覆盖的交互模式。

📍 里程碑
M0写 Remarker Protocol Spec：定义颜色语义（🟡🟢🔵🩷）+ 行号格式 + Agent 响应规则 M1AGENTS.md 插件化：Remarker 规则从硬编码改为可选 include M2团队 Dogfood：邀请 2-3 同事在真实 review 场景中使用 M3Protocol 开源：让其他 Agent 工具也能接入 Remarker 标注格式
✅ 成功标准
  • Protocol Spec 发布，Agent 能按规范解析标注并精确修改
  • 至少 1 个非 Kyle 用户在真实工作中持续使用 >2 周
⚡ 本周立即行动
  • 写 Remarker Protocol Spec v0.1（颜色语义 + 行号格式）
  • 将 AGENTS.md 中的 Remarker 规则改为插件模式
  • 回复 Ding 的推文，阐述 Remarker 的差异化定位
🔴 诚实挑战：目前只有 Kyle 一人在用。如果 M2 阶段团队不自然采纳（不推不拉），就诚实承认这是个人工具而非产品。Protocol 开源的前提是协议本身足够好——如果标注格式在真实使用中频繁需要修改，说明还没稳定到可以固化的程度。
