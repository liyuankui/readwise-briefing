System One 决策模型接入推荐重排层 — PoC 提案

速览：Jev（TypeSafe AI，2026-09-15 发布）开启 "System One Model" 范式——放弃文本生成，单次 forward 直出 typed decision（classify / route / score / rerank）与置信度，官方宣称在此类任务上智能与现有 LLM 相当、快 >100x、便宜 200x；开源社区已有接口复现 OpenJev（基于 Qwen3.5-4B，MIT，单次 forward 读 typed logits，无解码循环）。本提案验证：此范式能否替换推荐重排层中用生成式 chat model 打分的环节。

1. 核心主张

重排层的 LLM 打分不需要"生成"，只需要"判断"——用 System One 决策模型（单次 forward 直出 score + 置信度）替换 chat model 逐条打分，在离线效果不低于基线的前提下，把该环节成本与延迟各降一个数量级，使 LLM 级智能首次具备进入在线主链路的条件。押注范式而非厂商，5–6 周内可证伪。

追问预埋：

  • 为何不是"换更便宜的 LLM"？——范式差异：解码循环 vs 单 forward，是换账本，不是打折。
  • 为何现在？——接口复现已开源，验证窗口成本极低；正因其新，故只做带硬止损的期权。

2. 锁定痛点：重排层用 chat model 打分的成本结构

# 痛点 机制
P1 付"生成"的钱，买"判断" 只需输出 1 个分数 token，却须跑完整 decode 循环；prompt 含用户画像/行为序列/商品特征，prefill 千 token 级
P2 成本随候选数线性爆炸 重排 top-N 候选逐条调用；合批则 prompt 膨胀且候选互相干扰
P3 延迟进不了在线预算 解码 + 长 prefill 使 P99 远超重排层毫秒级预算 → 只能异步预打分（损失新鲜度）或缩小候选集/流量
P4 输出不可控 自然语言需 parse，格式漂移、无原生置信度，稳定性靠兜底逻辑维持

净效应：智能重排被成本锁死在"边缘异步"位置；扩展瓶颈是钱与延迟，不是效果方向。

3. 实施里程碑（总计 5–6 周，主力 1 名工程师）

里程碑 内容 时长 Gate / 产出
M0 基线冻结 从历史日志抽样构建评测集（用户上下文 × 候选集 × 行为标签）；跑通 chat-model 打分离线基线 0.5–1 周 固化 benchmark：GAUC / NDCG@10 + 成本/延迟基线

M3 影子 + 小流量 影子模式量 P99 与稳定性；1–5% 流量 A/B 2 周 P99 达标 + 核心指标不显著为负
M4 决策 三选一：全量 / 继续优化 / 止损；同步评估 Jev 商用 API 合规通道（仅对照） 0.5 周 一页决策文档

维度 指标 通过线

分桶稳健 尾部 query GAUC 跌幅 ≤ 3%

5. ROI 与业务影响

  • 成本面：重排打分环节降一个数量级 → LLM 打分从"小流量/异步"进入"主链路全量"变为可负担。
  • 延迟面：ms 级响应 → 重排候选集可由 top-20 级扩至 top-100 级，智能重排覆盖面数量级提升。
  • 能力面：原生置信度 → 首次可做分层路由（高置信直出、低置信升级大模型或规则），架构上出现"便宜的智能层"。
  • 复用面：typed-decision 服务建成后，意图分类、流量路由、风险分级同架构复用。
  • 投入产出：1 人 × 5–6 周 + 一张 GPU；失败上限 = 1 人月，成功上限 = 主链路成本结构改变。

6. 风险与缓解

风险 事实 缓解
Jev 闭源 权重/训练不公开，宣称不可独立复验；用户数据发外部 API 有出境合规问题 生产默认自托管；Jev API 仅做对照实验且只用合成/脱敏数据
OpenJev 仅接口复现 README 明言不复现模型与训练，效果上限 = Qwen3.5-4B，非 Jev 定位为"范式验证器"；M2 硬 Gate 止损；跟踪社区 2–4 周内独立评测
生产依赖 范式发布仅数日，无生产案例，接口易 breaking change 自持 typed-decision 抽象层，底层模型可热替换（4B / 未来开源权重 / 自训分类头），不深耦合任何一家
效果风险 pointwise 单 forward 可能弱于 listwise 生成式；4B 对长尾意图理解存疑 精排模型进基线；分桶评估；置信度路由回退
工程栈 Python/GPU 推理非团队主力栈 复用 K8s；单卡起步；云 GPU 过渡

7. 本周立即行动（3 件）

  1. 冻结评测集（1 人日）：抽样历史曝光-行为日志，固化 benchmark 与打分格式。
  2. 部署 OpenJev（0.5 人日 + 云 GPU）：跑通 typed rerank 接口，记录单条延迟/成本初值（Mac 不可行，需 CUDA）。
  3. 60 分钟对打 spike：同一批候选，OpenJev vs 现有打分方式，产出三维对比表（效果/延迟/成本）→ 用数据决定立项与否。

8. 诚实挑战（本提案的已知漏洞）

  1. 归因混淆：OpenJev 输了，分不清是范式不行还是复现不行；赢了，也证明不了 Jev 本尊。PoC 结论天然带星号。
  2. 参照系偷换：重排层真正的在位者不是 chat model，而是又快又便宜的精排 DNN。提案动机是"chat model 太贵"，落地对手却是"精排模型已经够用"——M2 若不含精排基线，整个论证是打稻草人。
  3. pointwise 结构性劣势：LLM rerank 文献中 listwise 常优于 pointwise；typed 单 forward 天然 pointwise，可能天生吃亏，需补 listwise 变体实验方可下结论。
  4. 机会成本：搜索个性化主线（待优化的 feed 路 + 标签体系 A/B）正吃人力，此 PoC 一旦超过 1 人投入，边际收益大概率为负。
  5. FOMO 承认：信号源是 hype 型推文（同一条连实时交易都吹了），技术发布仅 3 天。最诚实的定性：这不是战略判断，是一份行权价约 1 人月、5–6 周到期、带硬止损的看涨期权。

Decision Model 替代 LLM-as-Judge：AI 编程工具评测项目提案

2026-09-18 · Draft · 适用范围：AI 编程工具评测项目（coding model × harness 选型）的评分环节，不改变被测对象本身。 信号来源：Jev（TypeSafe AI 2026-09-15 发布的 System One Model）及开源复现 OpenJev（MIT，4B 底座），已多信源验证。本提案只取其范式，不依赖官方服务。

1. 核心主张

judge 环节本质是判别任务（classify/score），如今却用生成式 LLM 逐条写评语来完成——把它换成 decision model（typed criteria → 单次 forward → 判定 + 置信度，低置信度回退），judge 成本与延迟降一个数量级（机制上近乎确定，PoC 实测自证）；一致率能否提升取决于 rubric 显式化程度，本提案用对照实验把两件事分开归因，不混着讲故事。

必被追问 回答
便宜 10 倍，质量掉不掉？ 设非劣性硬门槛（§4），任一主指标显著劣于现 LLM judge 则不上线；混合回退兜底
一致率约六成，根因是模型还是 rubric？ 正是本提案要回答的问题：先测人人一致率（M1），再用 2×2 实验分离归因（M3）
为什么自建而不直接买 Jev？ 接口模式（criteria / options / confidence）是资产，权重可替换；不锁供应商

2. 锁定痛点

judge 是全流水线调用量最大、成本最高的环节，四个痛点互相咬合：

# 痛点 表现 后果
P1 范式错配 判别任务用生成式模型：解码循环写评语，再解析回结论 慢、贵、输出格式漂移
P2 成本钳制样本量 judge 按旗舰 LLM 计价，扩样本即成本爆炸 样本小 → 候选模型间评分无显著差异，选型证据不足
P3 一致率天花板 judge 判定与人工复核一致率仅约六成 评分可信度存疑，采购支撑弱
P4 无原生置信度 生成式输出无校准概率 无法路由，人工复核只能全量铺开

关键耦合：P2 是 P3 的放大器——样本小到连"模型间谁更好"都检不出。降 judge 成本的直接回报不是省钱本身，而是统计功效（样本量 × 频率）。

3. 实施里程碑（约 6 周，0.5 人力 + 小时级云 GPU）

M1｜金标集与根因诊断（第 1 周）

  • 抽 150–200 条已复核样本，双人独立盲标，测人人一致率（Cohen's κ）
  • 现行 judge prompt 逆向拆解为 typed criteria 草案：3–5 维度 × 3–5 档位，每档操作化定义
  • Gate：若人人 κ 也仅约六成 → 根因在 rubric，先修标准再谈换模型
  • 产出：金标集 v1、typed criteria v1、根因结论一页纸

M2｜Decision Judge PoC——自建，仿 OpenJev 接口模式（第 2–3 周）

  • 接口模式：runtime-defined criteria + typed options + option-logits 置信度，不绑定 OpenJev 权重
  • 双 backend 并行：a) 云 CUDA GPU 跑 OpenJev（4B 底座）；b) 等价路径——任意暴露 logprobs 的小模型 + 约束输出读选项概率（Bun + TypeScript 统一封装，上层流水线接口不变）
  • 产出：实测单条延迟/成本/批吞吐，对照官方宣称（>100× 快、>200× 便宜）

M3｜对照实验：分离 rubric 与模型（第 4 周）

  • 设计：{旧 rubric, 新 typed rubric} × {LLM judge, decision judge}，人工金标为锚
  • 指标：一致率、κ、校准（ECE / 可靠性图）、成本、吞吐
  • 产出：归因清晰的实验报告——涨了多少，记谁的功

M4｜混合流水线集成与扩量（第 5–6 周）

样本 → decision judge（typed 判定 + 置信度）
        ├─ 高置信 → 直接入表
        └─ 低置信 → 回退：大模型 judge / 人工复核
  • 全量重跑评测，样本量扩 5–10×，出含显著性检验的选型对比报告
  • 产出：v2 评测流水线 + 模型选型报告

维度 指标 PoC 通过线 挑战目标

7. 立即行动（本周，各 ≤1 天）

  1. 双盲标注启动：抽 150–200 条已复核样本，两人独立盲标（各约 2–3 小时）——下周即得人人一致率，直接检验 rubric 假设
  2. typed criteria 草案：现行 judge prompt 拆成维度 × 档位 × 操作化定义，AI 起草 + 一轮人审
  3. OpenJev 实测：云租 CUDA GPU 跑通 demo，实测单条延迟与批吞吐，一页纪要对照官方宣称

三件事合计不足 3 人日，任一结果都直接改写 M2–M4 取舍。

8. 诚实挑战（自己先捅漏洞）

a) 最大漏洞：一致率约六成，根因多半在 rubric，不在模型。 旁证：换不同 judge 模型，一致率与模型间差异都不显著——若模型能力是瓶颈，换模型应有位移；而人对"代码质量：良好/及格"这类模糊标准同样无法稳定一致。换 decision model 本身并不治这个病。它唯一的贡献是 typed options 容不下模糊措辞，被迫把每个档位写成可操作定义——若一致率因此上升，功劳应记在 rubric 工程，decision model 的确定性收益仍是成本与吞吐。本提案把这个假设当实验对象而非前提：M1 人人 κ 低于 0.6 就先修 rubric；若最终证明 rubric 才是全部答案，提案依然成立，只是主角换成 typed criteria，decision model 退居降本角色。

b) decision judge 丢掉了评语。 LLM judge 的自然语言理由对调试评测体系本身有价值（知道为什么错），typed 输出只有判定与置信度。缓解：低置信与抽样样本保留大模型评语；typed 维度命中本身即结构化归因。

c) 经济账可能不成立。 若 judge 环节当前绝对开销本就不大，降 90% 的绝对值覆盖不了 6 周投入。本提案真实回报是吞吐与统计功效，省钱是副产品；若 KPI 只有"省 judge 钱"，先算绝对值再立项。

d) 信号纪律。 原推文中「OpenCLI 配合 Jev」为作者个人玩法，无公开集成路径，本提案不依赖；推文的兴奋不构成证据，§7 的实测才算数。

8. 诚实挑战（本提案的漏洞）

挑战一：这就是 FOMO 吗？ 一半是。信源是典型营销号，推文本身信息量≈0；仓库规模真实（fork 比例健康、昨日仍活跃），但"不用会死"不成立。信号的合理权重只是：「工作流-DSL」模式在视频域出现了开源标杆。本提案的防御是全部回报压在与 Hypit 生死无关的模式学习上。

挑战二：B 路径隐含假设可能不成立。 本轮补验只确认了 SVML 的存在与宣称（词级锚定、可重跑组合），未读到语法/schema 本体——若 M1 发现它实为薄 prompt 包装、无严谨中间表示，M2 立即砍掉，提案降级为"信号已处理"。

挑战三：A 路径可能是伪需求。 小商家核心痛是「收到评价」（获取）而非「评价变视频」（再利用）；核心闭环留存未验证前叠加视频能力，是给未跑通的产品加砝码。最诚实的默认值是把 A park 到评价回收率/回复采纳率达标之后——保留 A 仅因首会在即、一页纸成本足够低。

挑战四：机会成本。 Kyle 的晚间时间是真稀缺资源。对照方案是"什么都不做，等 Hypit 出现争议或竞品再回看"——若 M0 结果平庸，后者才是对的。本提案的真实赌注只有前 15 分钟，其余皆条件分支。
