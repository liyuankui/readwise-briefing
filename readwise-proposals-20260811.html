Proposal 2：Shopify SKIP LOCKED 洞察 → IKEA MPC 迁移

Store POS Eng Baseline AI Coding Eval PostgreSQL

核心主张

不要照搬"一行一单位"——那可能是过度工程化。真正可迁移的是三件可立刻产生价值的东西：
① 一个 PG 版的 SKIP LOCKED 并发预留范式（PG 比 MySQL 更干净，无 gap lock 坑）；
② 把 Shopify 的"瓶颈不在预期处"反教训变成 MPC 的诊断 checklist（连接池/PosLog 同步路径）；
③ 把这份 Shopify → PG → MPC 的迁移推演本身，做成 AI Coding Eval 的高信号 judge case。

诚实版：Shopify 的 schema 设计是否适用，取决于 IKEA 库存模型是不是"离散可售单位"型——这点现在不确定，§诚实挑战 详述。

锁定痛点（三个候选，推荐 A）

候选场景匹配度现实依据本周可验证
A. C&C 订单结算的并发防超卖（高并发收银）🟢 最高C&C 结算 2MM；全国 rollout 后同一商场多台 ECO 机台并发；POS Phase 2 是新代码，无历史包袱是
B. 退单退库存的幂等/并发🟡 中0.5MM 但 fragile；退款合规会议要简化二次操作 → 并发简化后更易撞是
C. 叠券计价🔴 低计价是价格计算，非库存争用；SKIP LOCKED 不解决—

推荐锁定 A（C&C 防超卖）。理由：新代码现在介入成本最低；并发曲线随 rollout 陡增（latent 风险）；C 的痛点在 SPE/计价引擎，不在 Kyle 主控路径。

反诚实提醒：A 现在可能并不痛。试点 3 家门店、每店几台机，QPS 低到看不见。SKIP LOCKED 的价值只在 rollout 后兑现——这正是"工程基线"而非"救火"的定位。

🔑 PG vs MySQL 诚实处理（不可跳过）—— 这是 Proposal 严谨性的命门
Shopify（MySQL）坑PG 是否同样有IKEA 该怎么做
REPEATABLE READ 下 gap lock（含 supremum）阻塞补货→死锁❌ PG 无 gap lock（MVCC，默认 READ COMMITTED）PG 不用为这个降级隔离；保持默认
自增主键→双索引双锁⚠️ PG 用 heap 表，但 secondary index 仍可能二次锁复合主键思路可借鉴，但动机不同（索引选择性）
SKIP LOCKED 跳过被锁行✅ PG 9.5+ 同语义，官方明确推荐直接可用
inline 补货防惊群✅ 通用模式直接可用

结论：PG 比 Shopify 的 MySQL 路径更简单——不需要隔离降级 hack。但"一行一单位 vs 数量列"的 schema 抉择与 DB 无关，取决于业务模型。

MySQL 之坑（gap lock、supremum），PG 无之；MySQL 之巧（SKIP LOCKED、inline 补货），PG 亦有之。故迁移之难，不在 DB，在业务模型。
