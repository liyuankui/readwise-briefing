先验证「统一记忆层」，再决定是否引入 EverMe

Life OS 🌱 · Memory 支柱 ⚠️ Partial
Kyle 当前不缺"更多记忆工具"，真正缺的是一层可被多 Agent 读写、可沉淀为 case/skill、且可验证 ROI 的统一记忆层。

🎯 锁定痛点

最痛缺口不是"记不住文本"，而是跨 session 决策脉络丢失。换到新 session/新 Agent 时，Life OS 已讨论过的优先级、约束、排障经验需要重讲；一次方案比较难自动升级为可复用 case。

📊 成功标准

  • 二次启动补上下文时间↓70%
  • 20+ 高价值 case 可检索
  • 两个不同 Agent 共享同一记忆
  • 自动召回历史约束并被采纳

第1周：盘点现有记忆流（session-state/context/store_memory/AGENTS.md）与缺口地图

第1周：亲测 EverMe 最小链路（Agent A写入 → 新session Agent B查询 → 记录延迟/召回率/数据落点）

第2周：并行做轻量自建 PoC（会话摘要→结构化 case→检索）

第3周：AB 对比，决定 buy / build / hybrid

⚡ 立即行动（本周）

  1. 画出当前记忆地图与高频失忆场景（30分钟）
  2. 亲测 EverMe：从推文落地页拿真实仓库，按 README 安装，测试最小示例，记录"能否真正跨 session 召回"
  3. 同步做本地 PoC，用现有 context + session 摘要串联，对比可控性

🚩 诚实挑战

EverMe 的"越用越聪明"目前更像愿景而非证据。若无法回答"数据存哪、谁可读、如何删除、如何防泄露"，就不应进入 Kyle 的长期系统。EverMe 更可能是上层编排，而非替代现有方案。

CDH「AI时代工程能力标准」计划

Engineering Baseline 🔥 · AI Upskill ✅ Verified
把"会用 AI 写代码"升级为"能驾驭 AI 交付可维护系统"的团队标准，并纳入 Engineering Baseline 与人才发展。

🎯 锁定痛点

  • Junior 借 AI 快速产出，但无法评估代码质量 → "看似快、实则脆"
  • 评审标准停留在代码表面，未覆盖 AI 生成内容可验证性
  • 技术成果难映射到业务语言，向上管理只能讲效率

📊 成功标准

  • AI 相关 PR 测试覆盖率 ≥80%
  • 高风险缺陷回滚率↓30%
  • PR 中"不可维护"问题占比↓
  • 每月沉淀1份"技术→业务影响"案例

第1-2周：定义 AI Engineering Ladder，映射工程梯度、测试、评审、ownership（参考 jorgef/engineeringladders ⭐8.5K）

第3-4周：选 1-2 个团队试点，建立 AI Coding Guardrails

第5-8周：上线评审清单与测试门禁，纳入 PR 流程

第9-12周：复盘数据，形成管理层可读的 Value Demo 模板

⚡ 立即行动（本周）

  1. 拉 60 分钟 workshop，定义 CDH 的 AI Coding 失控案例与能力缺口
  2. 选一个活跃团队，试行 AI PR checklist + 测试门禁
  3. 基于 Engineering Ladders 起草"AI时代工程能力标准"草案

🚩 诚实挑战

若没有真实项目数据支撑，此提案会沦为口号；若不接入晋升、评审、质量门禁，也只是培训材料。关键不在"讲 AI"，而在把能力标准嵌入日常交付流程。

IKEA Skill Hub 质量评分层

IKEA Skill Hub 🛠️ · v5/v6 ⚠️ Partial
把"Skill 体检"内建为 Skill Hub 的质量评分层，让 51 个 Skills 不只"能上架"，更能被准确发现、放心使用、持续优化。

🎯 锁定痛点

  • description 过长挤占 prompt budget
  • 功能重叠导致 Agent 误触发
  • 部分 Skill 长期无人用却占曝光
  • 用户"看得到多，看不清好坏"

📊 成功标准

  • Top 20 Skills description 长度↓30%
  • 重复 Skill 识别准确率 ≥80%
  • 高质量 Skills 点击转化率↑20%
  • 低使用+低评分 Skills 8周内↓25%

M1：定义三类指标：描述长度、语义重复度、使用频率

M2：在多仓索引流程中生成质量分与风险标签

M3：前端展示质量 Banner、排序权重与筛选器

M4：接入反馈闭环，支持维护者按指标整改

⚡ 立即行动（本周）

  1. 对 51 个 Skills 跑一次离线审计，产出 baseline（description 长度分布图）
  2. 在 v5 PR 中预埋质量字段 schema，不阻塞多仓上线
  3. 选 10 个高曝光 Skill 做 description 压缩与去重试点

🚩 诚实挑战

这不是"再加一个功能"，而是给 Skill Hub 引入治理权。若没有 usage 数据、维护责任人与整改节奏，评分体系会迅速沦为装饰层。频率低 ≠ 价值低，评分需避免黑箱总分。

AI Upskill Trainer 🔥 · ACP + 工具演进 ✅ Verified
把"ACP 协议认知 + 新一代低成本 CLI/Agent 工具雷达"嵌入讲师团机制，不再只教 Prompt，而是教"未来工作界面 + 工具判断力"。

🎯 锁定痛点

当前课程若仍停留在通用 Prompt 与单点工具演示，6-8 周内内容将滞后：讲师无法解释 IDE 原生 Agent、ACP 协议互通、自主编码 Agent 的变化 → 学员转向外部博主 → 内部培训公信力下降。

📊 成功标准

  • 4周内：1套更新课件 + 3个 demo + 8位讲师通过试讲
  • 学员能正确说出"何时用 Chat/CLI/Agent"，正确率 >80%
  • 至少 2 个团队开始试用新工具

第1周：建立"前沿信号池"：ACP、OpenCode、Gemini CLI、Goose/OpenHands 每周快报

第2周：新增 L0.5《AI 工具演进地图》与 L2.5《CLI/IDE/Agent 实战分层》

第3周：产出 3 个标准 demo：同任务分别用 Chat / CLI / Agent 完成

第4周：讲师团试讲与复盘，沉淀统一话术；对业务学员灰度开班

⚡ 立即行动（本周）

  1. 完成《AI 工具演进地图》一页稿（Chat→CLI→Agent→ACP）
  2. 选 1 个真实开发任务做 Chat/CLI/Agent 三路对比
  3. 组织讲师团 30 分钟前沿 briefing，统一口径

🚩 诚实挑战

ACP 仍早期，不能包装成已成熟标准；OpenCode stars 数推文可能夸大，需交叉验证。信息差能带来领先，但缺少企业场景落地与合规约束时，领先只会变成"新工具猎奇"。

Trustworthy MPC Agent Guardrail Framework

Store POS 🔥 · Life OS Trust层 · Responsible AI ✅ Verified
以"人控、边界、透明、问责、协作"五原则为骨架，先管住高风险决策，再逐步释放自动化能力。

🎯 锁定痛点

POS Agent 出错 ≠ 普通 Agent 出错。MPC 覆盖计价/下单/PosLog/逆向，任一失真直接引发财务错账、库存失真、退货欺诈、税务合规风险，且跨系统扩散。交易系统比知识型场景需要更强的 Trustworthy 框架。

📊 成功标准

  • 计价正确率 ≥99.95%
  • PosLog 对账差异 <0.1%
  • 高风险动作 100% 可追溯
  • 异常回滚 ≤5 分钟
  • 人工介入率首季↓30%

M1：梳理 POS Agent 高风险决策清单与人工接管点

M2：为计价/下单/退货建立 policy boundary 与 action allowlist

M3：上线全链路 trace、decision log、evidence log

M4：建立离线 eval + 灰度演练 + 异常回滚机制

⚡ 立即行动（本周）

  1. 召开 POS Agent 风险建模 workshop（邀 MPC 负责人）
  2. 选"Cart 计价"场景做 Trustworthy MVP（最小化验证）
  3. 起草《MPC Agent Control Standard》并标注 Responsible AI 白皮书复用章节

🚩 诚实挑战

五原则方向正确，但在中国 IKEA 语境下需补足四项本地化要求：数据出境、个人信息最小化、审计留痕、人工复核责任归属。否则框架易停留在原则层，难支撑真实监管与内控。
