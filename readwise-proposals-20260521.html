3. TUI 式微 → 分层 AI 工具策略

AI UpskillLife OSBrowser Automation
TUI 不是在死亡，而是在回归其最适人群；团队应从"统一 CLI"升级为"GUI 扩覆盖、CLI 保杠杆、Workflow 做桥梁"的双轨策略。

右工具-右人群策略

人群主界面适合任务
业务/BA/非技术GUI/Desktop临时任务、文档生成、信息整理
普通工程师Hybrid日常开发、调试、PR 协作
Senior/StaffCLI/TUI复杂改造、系统集成、长链路任务

对 Life OS 的含义

CLI 继续做"内核"，但要补 GUI 入口、模板化任务、可观察层。

对 Upskill Trainer 的含义

从"教工具"改成三层教学：L1 GUI-first → L2 Workflow literacy → L3 CLI power-user。

4. Implementation Notes → 团队交付规范

Engineering BaselineAI CodingCode Review
对所有"非微小改动"，要求同步维护 implementation-notes.md，把"为什么这样改"变成可审阅、可验证、可交接的交付物——它是 delivery closure 的证据链。

定位

不是第 6 份 Harness 宪法文件，而是受 OPS 约束的标准执行证据。慢变量进 Harness，快变量进 Notes。

新工作流

VISION → SPEC → implementation-notes → code → OPS verification → delivery closure

对 Code Review 的影响

Reviewer 顺序改为：先读 notes，再看 diff。预期减少 30%+ "解释型往返"。

成功标准

指标目标
Reviewer "解释性问题"占比下降 30%+
PR 首次通过率提升 20%+
非微小改动 notes 覆盖率>80%
delivery-closure 有证据链占比>90%
⚡ 本周行动：
  1. 定标准：何时必须写 notes + 最小模板 + reviewer 顺序
  2. 选 2 个真实任务试跑（1 个 AI 主导 + 1 个多人协作）
  3. 在 project-harness OPS 模板中加入 Implementation Notes Protocol
🎯 诚实挑战：它默认团队已有稳定的 SPEC discipline。若 SPEC 本身松散，notes 只会记录混乱。前 2-3 周可能先变慢（学习期）。Notes 不能替代真正的验证——只能证明"你怎么想的"。
