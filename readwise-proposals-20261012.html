P1 · 简报管道补「信任验收层」

信任 = 不丢、不装、不哑

信号：Anthropic 长期自动化方法论（转述已直读核验）· 连接：P3 无人值守验收 / 现有 4:00 管道
管道已证明「能跑」，未证明「可信」。三个机制增量改造，不换架构：书签事务化（state.json 推进移到 push 成功后）· 来源失败显式化（失败≠无新内容，置顶告警）· 心跳一行 Clean（journal frontmatter 固定格式）。

失败必达（双通道）

管道内：catch → Bark 推 iOS（不依赖 GitHub）；管道死：GitHub Actions 云端死开关每日 05:10 检查当日简报存在，缺席即警报。首个事件触发任务：本地 launchd WatchPaths 监听 inbox/（防抖+单实例锁），不上云。

🔴 诚实挑战

  1. 六点 guardrails 系转述概括，落地前须读 Anthropic 原文对齐，防对转述过拟合。
  2. Clean ≠ 读对：心跳只证明「跑了」，Eval 抽查才是信任的另一半。
  3. 事务化代价：以「至多一次重复」换「零丢失」，需显式接受。

P2 · 评测升级为「爬山改进环」

eval-as-gate + hillclimb

信号：Claude evals + hillclimbing（官方）· 连接：NL 断言层 / Jev / Decision-1
评测非一次性裁判，乃常驻基建：改动即回归（L1 硬门），多变体并行择优（Jev 主判 + Decision-1 候补 + 双判仲裁 L3）。NL 断言层恰为地基，爬山环是其上第一个应用。

防过拟合三件套

dev/holdout 分割（70/30，爬山只见 dev）· 变体生成禁见评测集 · 连续 K 轮无提升注入大步长变体；负样本库显示「胜因=迎合 judge 措辞」即冻结该维度。

🔴 诚实挑战

  1. 爬山可能把产品带向评测偏好而非真实需求——「评测与真实价值的对齐」本身无评测，盲飞维度须定期人工校准。
  2. judge 未达标前 hillclimb 或不该开：57-59% 一致率下择优近掷硬币——MVP 先只上 gate，一致率升到 ~75% 再解锁爬山。

P3 · 借「Agent-Native 基建」趋势修订 opencode 提案

工具价值主轴：从「人用 GUI + 单价」移向 agent 可调用性

信号：gcloud→Agent API（Reader 存读）+ magpie + Microsoft-Decision-1 + Routines/Cowork · 连接：opencode-proposal F2-F5
opencode 提案升维：不作 Copilot 廉价替代（省 28% 的论证随单价下探贬值），而作 agent-first 终端入口——选型看 agent-first 程度，单价只是结果。工具清单评估框架新增「Agent 可调用性」维度（headless 入口/模型路由/审计日志/锁定度四问）。

30 分钟论据补强

三信号各写一句「它改变了什么」（CLI→API / 订阅→路由 / 通用→决策专用），合成附录《基础设施在为 agent 重排》贴入 draft-v1 §2/§4，成本表旁加「agent 可调用性」速评列。

🔴 诚实挑战

  1. 趋势判断可能早于采购周期（以季/年计）——对冲：绑能力维度而非厂商，锁评估视角不锁产品。
  2. 「可调用性」会被安全团队读作风险放大器——维度必须与审计、白名单捆绑入框架。
  3. 三信号皆出自硅谷/开源社区，内部需求证据薄——以 Qoder 试点数据补内证。
