pi-autoresearch：AI 自研究革命化测试与 CI
Shopify 有 974 个测试才能跑 autoresearch。我们覆盖率近零，必须先建地基——300× 拿来激励可以，拿来汇报是造假。
🎯 锁定痛点
IKEA CDH Java 服务测试覆盖率极低 → CI pipeline 依赖手工验证 → 构建时间长但没人敢优化（怕破坏未测试的功能）
📅 里程碑
M1 2w基线测量：time mvn clean verify 拿到构建时间 + 覆盖率数字
M2 4wAI 测试生成试点：选 1 个高频修改模块，AI 生成单元测试达 60% 覆盖率
M3 6wCI 并行化：测试分组并行执行，构建时间减少 30%+
M4 10wAutoresearch 试验：在有足够测试的模块上跑 AI 自研究优化
📊 成功标准
试点模块测试覆盖率从 ~0% → 60%+
CI 构建时间减少 30%（可度量，不吹 300×）
至少 1 个 autoresearch 优化案例可在 Digital Sharing Days 展示
⚡ 本周行动
time mvn clean verify 拿到第一个构建时间数字
读 Shopify/Karpathy autoresearch 原文建立判断力
找团队里最恨等构建的人聊 30 分钟
🚩 诚实挑战
漏洞：Java 生态 ≠ JS 生态。Shopify 的 300× 来自 React 组件测试特性，Java 的 Spring Boot 测试启动成本是结构性的，不能简单类比。必须先拿到 baseline 数据再说话。
漏洞：团队 11 人，日常交付压力大。额外写测试的带宽从哪来？需要经理级别的优先级保护。

Type-First Engineering：类型签名 = AI 的缰绳
类型签名不是代码风格偏好，是约束 AI 行为空间的 Ontology——命名即存在，边界先于内容。
🎯 锁定痛点
AI 生成代码时，类型不完善 → 运行时错误难追踪 → 边界条件被忽略 → 维护者无法快速理解 AI 生成的逻辑
📅 里程碑
M1 1w基线扫描：统计 TS 项目中 any 使用量 + Java 项目中 @Nullable 缺失率
M2 2w团队 Lightning Talk："类型签名 = AI 缰绳"（不提 Ontology，用工程语言）
M3 4w起草 3 条类型约定：禁 any / 返回值必须声明 / 接口优先
M4 8wAI Coding 模板集成：AGENTS.md 增加类型优先规则，AI 生成代码自动遵守
📊 成功标准
TS 项目 any 使用量下降 50%
新 AI 生成的 PR 中类型完整率 > 90%
团队理解"类型 = 约束 AI"的人数 > 70%
⚡ 本周行动
跑 grep -r "any" --include="*.ts" | wc -l 统计现状
准备 15 分钟 Lightning Talk 素材
起草 3 条类型约定初稿
🚩 诚实挑战
漏洞：团队主力写 Java（已强类型），对 TS 类型严格度的感知可能不强。需要找到 Java 侧也受益的切入点（如 @Nullable 注解、Branded Types）。
漏洞："类型签名重要"是正确但不新鲜的观点。真正价值在于将其与 AI coding 实践绑定——没有 AI 上下文，这只是老生常谈。

PRATA 架构演进：消息管道 → 神经系统
保持 E2E 加密底座不变，在 Watcher 层引入可插拔 Agent Runtime 适配器——bun:sqlite + FTS5 已是最优解，不需要迁移。
🎯 锁定痛点
PRATA v0.2 是优秀的消息管道，但 Watcher ↔ Copilot CLI 集成缺少标准 hook interface → 每接一个新 Runtime（Claude/OpenAI/Gemini）都要写胶水代码
📅 里程碑
M1 1wHook Interface 提取：从现有 Watcher 代码中抽象 AgentRuntime 接口
M2 2wClaude Runtime PoC：子进程调用 Claude CLI，验证消息 → 推理 → 回复链路
M3 3wMemory Schema 设计：FTS5 全文搜索 + 可插拔记忆层（对齐 Life OS Memory 支柱）
Gate⚠️ 决策门：2-3 人试用反馈后才启动 M4（多模型适配器）
📊 成功标准
新增 Runtime 适配器的开发时间 < 2 小时（当前 ~1 天）
Memory 检索延迟 < 50ms（FTS5 保证）
至少 2 名团队成员完成 Watcher 试用并给出反馈
⚡ 本周行动
从现有代码提取 Hook Interface（~2h）
Claude Runtime PoC：子进程调用验证（~1h）
Memory Schema 设计草案（~30min）
🚩 诚实挑战
漏洞：最大风险是"解决还不存在的问题"——当前 PRATA 没有用户抱怨 Runtime 不够多。设置决策门是对的，但要警惕过度架构。
漏洞：Claude Agent SDK 的 API 稳定性未知。子进程调用是最安全的隔离方式，但性能开销需要实测。

GEO 监测：AI 搜索中的隐形品牌风险
IKEA China 必须在 2026 建立 GEO 监测能力，否则在 AI 搜索引擎的回答中成为"隐形品牌"——用户问"沙发推荐"时看不到宜家。
🎯 锁定痛点
6 个盲区：① AI 搜索中 IKEA 品牌引用率未知 ② 官网内容不可被 AI 解析 ③ 无 GEO 归因闭环 ④ 宝尊内容产出未考虑 AI 可读性 ⑤ 国内/海外 AI 平台差异大 ⑥ 竞品 GEO 动向零感知
📅 里程碑
M1 2w基线盲测：5 个高频查询 × 3 个 AI 平台（ChatGPT/Gemini/Kimi），记录 IKEA 出现率
M2 4w追踪框架：基于姚金刚开源 skill 搭建 IKEA GEO 监测方案
M3 6w内容改造试点：选 1 个品类（如收纳），优化内容结构使其对 AI 友好
M4 8wSkill Hub 集成：GEO 监测封装为标准 Skill，可被其他团队复用
📊 成功标准
IKEA 在试点品类的 AI 搜索引用率从 baseline 提升 20%+
GEO 监测 Skill 在 Skill Hub 上线并被 ≥2 个团队使用
宝尊 Ontology 调研中新增"GEO 准备度"评估维度
⚡ 本周行动
30 分钟盲测：5 个查询 × 3 个 AI 平台，记录 IKEA 出现情况
宝尊内容模块访谈（酒令）加入 GEO 准备度问题
Clone 姚金刚 geo-tracking-plan 仓库，研究架构
🚩 诚实挑战
漏洞："内容不归你管"——GEO 优化的执行者是内容团队/宝尊，CDH 只能提供工具和数据。需要跨部门协作，而这正是最难的部分。
漏洞：GEO 是新领域，ROI 还没有行业基准。先做盲测拿到数据，才能判断投入是否值得。不能只因为是新趋势就冲进去。
